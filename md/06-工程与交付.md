# 第五部分　工程与交付：让系统经得起修改、失败和上线

一个原型能跑起来，只证明主路径曾经成功。真正交付还要回答：换一份输入会怎样，外部响应丢失会怎样，规则修改后旧功能是否仍成立，谁有权把结果变成动作，以及下一位维护者能否看懂并继续。

## 先写约束，再写代码

工程约束防止系统在快速生成中失去边界。每条都要能落到目录、类型、测试或运行检查，单纯的格式偏好不算约束。

| 约束 | 可执行的表达 |
|---|---|
| 浏览器不能执行任意命令 | 页面只提交类型化任务；服务端把任务映射到白名单运行器 |
| 领域规则不能散在页面里 | 关键状态转移由 `cases/<id>` 的领域模块检查 |
| 数据源不能被演示修改 | `dataset/` 只读；运行状态写入 `code/runtime/` |
| 首屏必须稳定 | 服务端与客户端使用同一份快照，不在首屏读取随机数或本地时间格式 |
| 高影响动作要有人负责 | 服务端按角色拒绝越权；确认动作记录操作者与业务版本 |
| 修改不能破坏旧案例 | 先跑聚焦测试，再跑共用合同、类型检查和生产构建 |

目录结构只服务依赖方向。共用控件可以被案例使用，案例领域不能反过来依赖某个页面；数据读取可以被领域服务调用，读取器不能偷偷决定业务状态。发现两个文件相似时，先确认它们是否真的有同一变化原因，再决定是否抽象。

## 用七级阶梯判断“现在要不要做”

面对一个看起来很先进的想法，按下面顺序检查：

1. 当前业务决定是否真的需要它；
2. 现有流程能否用更小改动完成；
3. 数据是否支持这项判断；
4. 权限与责任是否清楚；
5. 失败后能否恢复；
6. 能否写出可重复的验收；
7. 收益是否值得新增的运行与维护成本。

只在前一层回答“是”后再向下。一个服务端函数能完成的工作，不因为名称里有 AI 就拆成三个 Agent；一次固定查询能回答的问题，不为了展示 Agentic RAG 而增加循环；团队还没有独立发布需求时，不为“以后可能扩展”提前拆微服务。

## Skill 要像产品能力一样管理

Skill 的生命周期可以保持简单：草稿、复核、可用、停用。进入“可用”前检查触发条件、输入、输出、权限、固定样本和停止条件。停用后不再被新任务发现，但旧版本和旧结果仍能解释。

外部 Skill 先当成代码依赖审查：

- 来源和许可是否清楚；
- `SKILL.md` 声称的动作与脚本实际动作是否一致；
- 是否联网、读取凭据、写出项目范围或调用未声明命令；
- 固定样本能否得到稳定结构，错误输入是否明确停止；
- 新版本改变了哪些输出字段、权限或运行环境。

团队 Registry 保存的是可发现版本，不是“大家都能直接执行”的授权。Agent 仍只能使用当前任务开放的工具和路径。一个 Skill 即使通过安全检查，也不能替用户批准付款、发布、删除或设备控制。

## 交付分四级，不要一次跳到自动执行

| 级别 | 系统可以做什么 | 仍由谁决定 |
|---|---|---|
| 观察 | 收集、整理、标出缺口 | 人判断材料是否可信 |
| 建议 | 给候选、依据和不确定项 | 人选择方案 |
| 受控执行 | 在白名单内执行可恢复动作 | 人批准高影响动作 |
| 自动运行 | 在稳定规则和监控下持续执行 | 负责人设阈值、审计并可随时停用 |

升级不看演示效果，看连续运行材料：错误率、拒绝率、人工改判、恢复时间、成本和业务结果。建议写得好不等于可以自动执行；没有实际运行记录时，只能说明本地固定样例通过。

## 停止和升级写进任务，不靠临场感觉

每个长任务在开始前写明：最大轮数、时间或费用预算、哪些错误可以重试、哪些情况必须停、交给谁、需要带上什么材料。

```text
可重试：网络超时，且业务键可查询、动作幂等
立即停止：身份失效、输入越界、数据合同变化、结果将触发高影响动作
交接材料：当前对象、已完成步骤、最后成功结果、错误、剩余动作
```

“再试一次”不是通用恢复方案。若请求可能已在对方完成，先按业务键查询；若结果不可撤销，重试前必须确认幂等或由人处理；若同类错误连续出现，停止循环并修复输入、依赖或规则。

## 测试从业务不变量开始

测试金字塔在 AI 产品里仍然有效，只是多了模型和数据的不确定性：

| 层次 | 检查什么 | 示例 |
|---|---|---|
| 纯规则 | 计算、状态转移、不变量 | 缺原单号时不能提交补证任务 |
| 数据合同 | 字段、类型、范围、缺失 | 污染物全空记录进入待核验而非自动删除 |
| 组件与接口 | 角色、错误、持久化 | 普通人员提交主管动作返回明确拒绝 |
| 浏览器旅程 | 用户是否真的能完成决定 | 创建任务、刷新、换角色、复核 |
| 模型评测 | 固定样本上的结构和关键事实 | 摘要保留数字、来源与“等待人决定” |

模型评测不追求每个字相同。先固定必须出现、不得出现和允许变化的字段；把金额、权限、状态转移交给确定性代码；模型只承担生成、归纳或候选排序。修改 Prompt、模型或 Skill 后，让旧样本重新运行，避免解决新题却破坏旧题。

## 事件和分布式系统要主动制造坏天气

只测成功路径，看不到重复、乱序、超时和局部失败。至少加入四类检查：

1. 同一事件到达两次，只产生一次业务结果；
2. 旧版本事件晚到，不覆盖新状态；
3. 外部响应超时后，能查询已有结果而不是盲目再建；
4. 一个消费者失败时，其他结果保持可见并留下重试入口。

缓存测试也要包含权威数据变化、过期和穿透。RAG 测试要包含找不到、找到互相冲突的材料，以及检索内容夹带操作指令。A2A 测试要验证任务身份、状态和产物，而不是只看三个角色是否都输出了文字。

## 一次可复查的交付记录

交付记录保持短而具体：

```text
改了什么：文件与业务行为
怎样检查：实际运行的命令与用户动作
结果怎样：通过、失败或尚未具备条件
留下什么：截图、报告、输出文件或检查结果
下一步：唯一尚未完成的动作
```

“代码已生成”“测试应该通过”“模型效果很好”都不是结果。真实浏览器、当前测试、数据计算和供应商实际响应各自只能证明对应范围，不能相互替代。

## 人与 AI 怎样共同评审

AI 适合做全量扫描、交叉核对、生成候选和重复执行检查；人负责目标、取舍、责任和高影响决定。一次有效评审从三个角度看同一改动：

- 使用者：能否在当前页面完成此刻的决定；
- 领域负责人：规则、术语和责任有没有被改写；
- 工程维护者：错误能否定位，状态能否恢复，改动能否继续演进。

评审意见要指向具体对象、规则或旅程。没有新问题、既定检查通过时就停止；继续增加术语和流程不会自动让交付更可靠。

理论到这里结束。后面的二十四个案例不再逐个复述概念，而是把同一套判断放进退款、医院协同、模型准入、工业现场和日常经营，让角色真正点按钮、补材料、换人确认并留下结果。
