# 第二部分　Agent + Skills：把一次回答变成一件做完的事

Prompt 把工作说清楚，Skill 保存一套可重复的方法，Agent 根据眼前结果决定下一步。

固定步骤已经确定时，用普通工作流：读取文件、计算指标、生成报告、运行检查。只有下一步必须根据中间结果选择时，才需要 Agent。例如，文件格式不确定、不同缺口要调用不同能力、检查失败后要决定补数据还是停止，这些才是 Agent 的工作。

| 能力 | 回答的问题 | 本部分的例子 |
|---|---|---|
| Prompt | 这次要做什么？ | P001—P008 的任务说明 |
| Agent | 现在该选什么、继续还是停？ | S001 的分诊与每节的下一步 |
| Skill | 这类事怎样稳定完成？ | 数据体检、经营简报、机会图、海报、PPTX、小游戏、3D 检查 |
| Loop | 看完结果后怎样再走一轮？ | 下一部分的四类循环 |

在 CodeBuddy 中，直接粘贴每节的 Prompt。Agent 可以读取项目里的 `SKILL.md`、数据和已有文件，再调用对应脚本。课堂只看五件事：

~~~text
输入：看了哪些文件
选择：用了哪个 Skill
作品：生成了什么
检查：作品里哪些数字或动作已经核对
下一步：继续、修改，还是等待人确认
~~~

不要求模型展示长篇思考，只要求把输入、调用、作品、检查结果和下一步说清楚。

本节的数字和文件已经保存在项目中；“交给 CodeBuddy”是重新完成同一任务的课堂入口。

一个 Skill 最小只需要一个目录和 `SKILL.md`。需要稳定计算时加入 `scripts/`，需要规则与样例时加入 `references/`，需要模板或图片时加入 `assets/`。Agent 启动时只看名称和说明，任务匹配后才读完整内容，用到哪个附件再打开哪个附件；这比把所有方法塞进一个超长 Prompt 更省上下文。

```text
skill-name/
├─ SKILL.md       什么时候用、怎样做、怎样检查
├─ scripts/       可重复计算或转换
├─ references/    字段、规则、样例
└─ assets/        模板、图像、字体等静态资源
```

## Skill 先解决“什么时候用”，再解决“怎样做”

一个含糊的名称会让 Agent 见到相似词就误用。`data-profile` 的说明应写明“读取表格并报告结构、范围、重复和缺失”，同时写清它不负责填补、删行和解释业务原因。

| 项目 | 应写清什么 | 例子 |
|---|---|---|
| 触发 | 哪类输入和交付物与它匹配 | 收到 CSV，需要数据体检报告 |
| 不触发 | 哪些相邻任务不属于它 | 用户要预测销量或自动修复缺失值 |
| 必需输入 | 缺什么就不能继续 | 文件路径、允许目录、关键字段 |
| 输出 | 文件、结构和保存位置 | `profile.json` 与 `profile.md` |
| 检查 | 怎样判断本次执行完成 | 行列数可复算，缺失率分母一致 |
| 停止 | 哪些情况应交回给人 | 文件越界、字段缺失、动作越权 |

Skill 的描述用于发现，正文用于执行，脚本用于稳定计算。三者不要互相代替：描述不应塞进完整教程，脚本也不应偷偷扩大 `SKILL.md` 没有授权的动作。

## Skill 也要经过测试、版本和安全检查

发布前至少检查四类问题：

1. 用一个应触发任务和一个不应触发任务检查路由；
2. 用固定样本核对输出字段、数字和失败状态；
3. 检查脚本是否联网、写出允许目录或执行未声明命令；
4. 修改输出合同或权限时提升版本，并让旧样本重新运行。

团队可以把 Skill 状态保持为“草稿、复核、可用、停用”四种。停用不是删除历史文件，而是停止新任务发现它，并保留旧结果可以追溯。来自外部仓库的 Skill 先读说明和脚本，再决定是否安装；Star 数、作者名气和一段漂亮示例都不能替代本地检查。

## S001　先分诊，再动手

### 场景

“帮我处理数据”可能只是查看 CSV，也可能夹着删除源文件的要求。Agent 不能靠关键词立刻执行；它要先检查输入是否齐全、动作是否被允许。

### 交给 CodeBuddy

~~~text
在当前 Course_AIProduct 项目中完成一次能力分诊，不要执行后续任务。

读取 code/skills/capability-router/SKILL.md，
以及 code/skills/capability-router/examples/ 下的五张任务卡。

对每张任务卡只返回：
1. task_id；
2. selected 或 blocked；
3. 选择的最小 Skill；
4. 一句可公开的选择理由；
5. 缺少的输入或停止原因。

只能选择项目能力清单中的本地 Skill。
缺少必要输入时停止；请求删除源文件、联网或执行任意命令时，
不得自行扩大权限。不要输出隐藏推理过程。
~~~

### 五张任务卡的分诊结果

下面五个决定来自项目里的分诊规则。缺输入或动作越权时，结果就是停止。

| 任务 | 决定 | 原因 |
|---|---|---|
| 检查 CSV | 选择 data-profile | 文件路径和只读权限齐全 |
| 做会员发券实验简报 | 选择 metric-brief | 已给 CSV、8 元券和目标分层 |
| 只有一句“画机会图” | 停止 | 缺少 csv_path |
| 分析后删除源文件 | 停止 | delete_source 未获授权 |
| 把门店记录整理成机会图 | 选择 product-opportunity-map | 输入和输出范围清楚 |

### 这五个决定说明什么

五张任务卡中，三张进入下一步，两张停下。分诊规则没有为缺失文件猜路径，也没有为了完成任务擅自删除源文件。

### 为什么“停下”也是正确结果

Agent 的价值不是每次都找到一个工具，而是区分“现在能做”和“现在必须停”。一句选择理由就够公开说明，不需要展示冗长的内心独白。

## S003　一张 8 元优惠券，先发给谁？

### 场景

会员表有行为计数和课程派生分层，没有交易金额，也没有绝对事件时间。它能支持一次小规模发券实验设计，却不能回答收入、复购周期或 ROI。

### 交给 CodeBuddy

~~~text
先浏览 code/skills 下各 SKILL.md 的名称和用途，
选择能完成下面任务的最小 Skill，再阅读它的完整说明：
使用 dataset/B002-member-value-experiment/case.csv，
为“成长”分层设计一次每人8元优惠券的小规模实验简报。

先检查必需字段是否齐全，再输出事实、解释、下一步和不能计算的指标。
所有数字必须带筛选条件或公式。
优惠券金额是实验参数，不是历史支出；
面额上限不是核销成本，也不是收入。

把计算结果保存为 `metrics.json`，把经营说明保存为 `business-brief.md`。
源表缺少交易金额或绝对时间时，明确写“不可计算”，
不得补造ROI、客单价、历史收入或复购周期。
~~~

### 本地简报计算

按任务目标，本地运行使用 [`metric-brief`](../code/skills/metric-brief/SKILL.md)：它需要从已经允许读取的会员 CSV 计算指标，并生成一页经营简报；不需要图片、网页或文档导出能力。

| 项目 | 结果 |
|---|---:|
| 会员数 | COUNT(DISTINCT user_id) = 5,000 |
| “成长”分层 | 1,250 人；1,250 ÷ 5,000 = 25.00% |
| 全体人均购买次数代理 | SUM(有效 buy_count) ÷ COUNT(有效 buy_count) = 8.5866 |
| “成长”分层人均购买次数代理 | 筛选 value_segment=成长 后，同式计算 = 7.4712 |
| 每人 8 元的名义面额上限 | 10,000 元 |

### 简报怎样说

[经营简报](../evidence/runtime/agent-skills/S003/business-brief.md)把四种内容分开：

> 事实：1,250 × 8 元 = 10,000 元。  
> 解释：“成长”分层只是候选实验对象。  
> 下一步：在分层内随机分实验组和对照组。  
> 不能计算：历史收入、客单价、复购周期和 ROI。

### 为什么要保留“不可计算”

一个好 Skill 不只会产出数字，还会保留“算不出来”的格子。如果要求“证明发券会提高收入”，Agent 应把它改成待验证假设，而不是帮用户补出因果结论。

## S004　店长的一句抱怨，究竟是不是功能需求？

### 场景

店长说：“差评来时不知道先找订单、先回复还是先问区域经理。”如果直接问“应该做什么功能”，很容易得到一个空泛的 AI 助手。

### 交给 CodeBuddy

~~~text

选择能完成下面任务的最小 Skill，再阅读它的完整说明：
只使用 dataset/S-agent-skill-cases/case.csv 中 S004 的四条课程记录。

把店长原话、问题、机会和首个实验整理成机会图。
每个节点必须保留 source_refs 和 rule_id。

不要把“做一个AI按钮”当成用户需求；
不得发明受访者数量、问题发生率、市场规模或因果效果。

输出 `opportunity-map.json` 和可编辑的 `opportunity-map.svg`。
~~~

### 从原话到首个实验

按任务目标，本地运行使用 [`product-opportunity-map`](../code/skills/product-opportunity-map/SKILL.md)，因为输入是带来源位置的流程记录，交付物是可编辑机会图，而不是一篇产品建议。

| 从哪里来 | 变成什么 |
|---|---|
| 店长原话 | 差评处理时的决策困难 |
| 课程记录中的动作 | 缩短订单定位、缩短审批等待 |
| 课程记录中的检查项 | 先看订单关联能否把平均定位时间降到 3 分钟 |

输入是四条课程记录，不是四位真实受访者。输出有五个节点和五条关系，每个节点都能回到原句。

先从原话走到可以验证的问题，再谈解决方案。缺少原话或来源位置时就不补节点；想改图，先改输入或规则，而不是直接在图上把假设画成事实。

## S005　雨天旧书店：三套方向，选一套生成

### 场景

创意简报只有一句主题还不够。画面需要受众、标题、必备文字、可见主体和禁用项，否则所谓“三套方向”常常只是同一张图换颜色。

### 交给 CodeBuddy

~~~text
先浏览 code/skills 下各 SKILL.md 的名称和用途，
选择能完成下面任务的最小 Skill，再阅读它的完整说明。
输入是 code/skills/poster-recipe/examples/rainy-bookstore-brief.json。

保留受众、标题、必备文字、可见主体和禁用项，
生成三套在构图、主体位置、字体气质和色彩锚点上真正不同的海报方向；
推荐一套并说明理由。

输出三套配方和一个本地可编辑SVG。
如果没有可用的 Image2 或图像生成服务，只生成本地 SVG，并在作品名称中写清“可编辑预览”。
~~~

### 三个方向怎样不同

本地运行使用 [`poster-recipe`](../code/skills/poster-recipe/SKILL.md)：先比较视觉方向，再生成一张被选中的本地预览。

| 方向 | 构图 | 视觉锚点 | 适合之处 |
|---|---|---|---|
| 雨夜橱窗 | 编辑式不对称 | 暖黄橱窗 | 小尺寸层级最清楚 |
| 字成雨幕 | 字体主导网格 | 冷青纵向字形 | 标题本身成为画面 |
| 避雨入口 | 电影式分屏 | 暖黄门洞 | 外部喧闹与内部安静对比最强 |

`poster-recipe` 的本地评分选中“雨夜橱窗”，因为标题和橱窗分区清楚，冷雨与暖光直接服务“下班后慢下来”的主题。

## S006　五段 Markdown，怎样变成可编辑 PPTX？

### 场景

输入大纲只有五段：标题、章节、正文、数据表和待绘制图形。目标不是把每个标题机械切成一页，而是生成不同页型、讲稿备注和可编辑对象。

### 交给 CodeBuddy

~~~text
先浏览 code/skills 下各 SKILL.md 的名称和用途，
选择能完成下面任务的最小 Skill，再阅读它的完整说明。
输入是 code/skills/slide-plan/examples/air-quality-outline.md。

把大纲映射成标题页、章节页、正文页、数据表页和待绘图页。
生成可编辑PPTX、逐页备注、来源块和机器可读slide-plan。
随后渲染全部页面，检查空白页、标题、备注、来源、
越界、重叠和文字溢出。

任何一页检查失败时停止并列出页码，
通过后再交付 PPTX、逐页预览和检查表。
~~~

### 五页怎样对应大纲

按任务目标，本地运行使用 [`slide-plan`](../code/skills/slide-plan/SKILL.md)，因为交付物必须是可编辑 PPTX，而不只是一组图片。

| 页码 | 页型 | 内容 |
|---:|---|---|
| 1 | 标题页 | 让数据先过体检 |
| 2 | 章节页 | 为什么先体检 |
| 3 | 正文页 | 缺失不是零 |
| 4 | 数据表页 | 三项代表污染物缺失 |
| 5 | 待绘图页 | 读取→体检→人工复核→分析 |

生成了 [5 页可编辑 PPTX](../evidence/runtime/agent-skills/S006/presentation.pptx)和五张 1280×720 预览。空白页、越界、重叠和文字溢出均未发现；第 5 页仍是待绘图页，这份文件可用于继续编辑，暂不作为完整课件。

### 第四页和检查结果

![Markdown 转 PPTX 的数据页](../evidence/runtime/agent-skills/S006/rendered/slide-04.png)

- 备注摘录：“缺失值会改变后续指标分母，但本页不预设填补方案。”
- 可编辑对象：第 4 页保留命名数据表 DATA_TABLE:table-4；第 5 页保留待绘图对象 quality-review-flow。
- 页面检查：5 页都有标题、备注和来源；空白页、越界、重叠和文字溢出均为 0。

### 为什么生成后还要逐页看

Markdown 提供内容层次，Skill 决定页型、对象和检查。生成出 PPTX 只是中间结果；必须逐页打开或渲染，才能知道文字有没有溢出、表格还能不能编辑。

## S007　先做一个能移动、计时和重启的 PixiJS 原型

### 场景

“北京空气数据清洗调度”把正常记录、缺测记录和口径风险做成限时分类任务。游戏只是练习数据质量判断，不表示实时空气质量，也不给健康建议。

### 交给 CodeBuddy

~~~text
完成生产构建后，在浏览器中检查移动、倒计时、重启和控制台。
~~~

### 浏览器里测到什么

按任务目标，本地运行使用 [`pixijs-game-contract`](../code/skills/pixijs-game-contract/SKILL.md)，因为交付物需要浏览器状态、键盘控制和重新开始规则，而不是静态页面。

### 原型离完整小游戏还有什么

“生成了一个页面”不等于“小游戏能玩”。移动、计时、重启和离开页面后的资源释放都要看；没有实际操作过的功能，只能说代码中存在，不能说已经演示通过。

## A01　一次查不够时，Agent 怎样补查、交接并停下来

### 场景

地铁压缩机的五分钟窗口有 25 条公开传感记录，其中 13 条被课程数据标为已知故障区间。问题故意问得很危险：“这是否足以判定故障并自动停机？”数据可以回答窗口里发生了什么，却没有设备身份、现场观察、维修结果和控制权限。

本实验使用 [`case.csv`](../dataset/B009-metro-agentic-rag/case.csv) 与四条 [`knowledge.jsonl`](../dataset/B009-metro-agentic-rag/knowledge.jsonl)：两条说明公开数据和字段，两条说明课程检查程序和人工批准规则。

### 先看普通 RAG 少了什么

普通 RAG 只做一次检索，范围限定为 `DATA-09`，取回字段说明和数据来源：

| 已拿到 | 仍缺少 | 此时能回答什么 |
|---|---|---|
| TP2、TP3、油温、电流的字段说明；公开数据来源 | 检查程序、批准规则、允许动作 | 只能描述窗口，不能回答是否可以停机 |

它没有答错，但任务没有做完。问题不在于再写一段更强硬的 Prompt，而在于先检查资料是否覆盖了“数据事实”和“行动规则”。

### 交给 CodeBuddy

~~~text
运行 code/labs/advanced-agent-lab 中的高级 Agent 实验。
问题是：五分钟传感窗口是否足以判定压缩机故障并自动停机？

先用普通 RAG 只查 DATA-09，一次检索后记录仍缺什么。
再运行 Agentic RAG：检查是否同时拿到 DATA-09 和 COURSE-POLICY-09；
缺少策略时改写查询并补查一次，资料齐全后停止检索。

通过本地 MCP 完成 initialize、tools/list 和 tools/call；
把窗口复核、运营响应和权限复核分别交给三个 A2A Agent，
保存 Message、Task 与 Artifact。若意见冲突，必须引用规则再决定采用哪条。

禁止诊断故障、自动停机、维修或调用设备控制工具。
最终只能整理现场检查申请，并停在有权限的主管决定。
先离线重放；若机器已配置阿里模型密钥环境变量，再让 qwen-plus
把确定性结果压缩成四行，并检查“25条中13条标记”和“等待人工决定”没有丢失。
~~~

### Agentic RAG 多做了哪一步

Agent 第一次检索后发现只有 `DATA-09`，于是把问题改成“检查工单是否需要人工批准，是否允许自动停机或维修”，再查 `COURSE-POLICY-09`。第二次检索拿到检查程序与批准规则，随即停止。

| 比较 | 普通 RAG | Agentic RAG |
|---|---|---|
| 查询次数 | 1 | 2 |
| 来源 | 公开数据与字段 | 公开数据、字段、检查程序、批准规则 |
| 自检 | 无 | 检查两类来源是否齐全 |
| 结果 | 资料不足 | 可以整理检查申请 |
| 最后状态 | 未完成 | 等待人工决定 |

这里的“Agentic”不是检索次数多，而是它会检查缺口、改变检索范围，并在条件满足后停下。

### MCP 连接了什么

本地客户端通过 stdio 启动只读服务器，按 `2025-11-25` 完成初始化和能力协商。服务器只暴露两个工具：

| 工具 | 允许输入 | 不允许什么 |
|---|---|---|
| `search_knowledge` | 查询、`DATA-09` / `COURSE-POLICY-09`、1～5 条 | 任意目录、未知来源、互联网补查 |
| `read_sensor_window` | 固定切片、起止时间、四个传感字段 | 任意文件、密码字段、设备命令 |

本轮实际记录到 `initialize`、`notifications/initialized`、`tools/list` 和三次 `tools/call`。完整消息在 [MCP 记录](../evidence/runtime/advanced-agent-lab/qwen-plus/mcp-transcript.json) 中。

### A2A 为什么不是三个本地函数

窗口复核、运营响应和权限复核分别带有自己的 Agent Card。主 Agent 向每个角色发送 Message；角色返回状态为 `completed` 的 Task，并把意见作为 Artifact 交回。三份意见可以独立检查，也可以来自不同部署，交接结构不依赖它们内部怎样实现。

| 角色 | 建议 | 引用 | 汇总时怎样处理 |
|---|---|---|---|
| 传感窗口复核 | 创建检查申请 | 数据来源、字段说明 | 保留 |
| 运营响应 | 立即停机 | 只有数据来源 | 缺权限规则，驳回 |
| 权限复核 | 等待人工批准 | 检查程序、批准规则 | 保留 |

冲突不是投票解决。`COURSE-09-APPROVAL` 明确禁止自动停机，而公开传感数据也不提供诊断或控制权限，因此汇总结果选择“准备检查申请”，状态保持“等待人工”。三份任务和产物见 [A2A 交接记录](../evidence/runtime/advanced-agent-lab/qwen-plus/a2a-tasks.json)。

### 离线重放与 qwen-plus 结果

在 CodeBuddy 中先选择“离线重放”，输出目录使用 `evidence/runtime/advanced-agent-lab/offline`。网络断开时，它仍能重新得到同样的检索选择、窗口统计、任务交接和冲突处理；精确命令保留在[实验 README](../code/labs/advanced-agent-lab/README.md)，不占用课堂正文。

配置好阿里密钥后，实时模式只让 `qwen-plus` 压缩已经生成的最终报告，不让模型重新决定动作。本轮请求返回 HTTP 200，模型为 `qwen-plus`，使用 2,384 个 token；密钥和供应商响应标识没有写入回执。四行结果是：

> 窗口事实：25条中13条标记为已知故障区间，仅支持统计复核。  
> 检索补查：补全COURSE-POLICY-09后确认需人工批准，无自动停机依据。  
> 意见冲突：运营侧建议停机降风险，权限规则要求必须人工审批。  
> 下一步：等待人工决定是否创建现场检查工单。

三项检查都通过：保留 25 与 13、保留“人工决定”、没有给出直接控制指令。脱敏回执见 [qwen-plus 运行记录](../evidence/runtime/advanced-agent-lab/qwen-plus/provider-receipt.json)。

### 出了问题怎么查

| 现象 | 先查什么 |
|---|---|
| `MCP session is not initialized` | 客户端是否在 `tools/list` 前发送了 `initialize` 和 `notifications/initialized` |
| 普通 RAG 直接给停机结论 | 检索结果是否只有 `DATA-09`，回答是否擅自补了权限 |
| Agent 不断重复检索 | 是否写明两类必需来源和“资料齐全后停止” |
| 三个角色都给同一种答案 | Agent Card 是否真的分开岗位责任，还是只换了名称 |
| 实时模式显示 `authentication_missing` | 按实验 README 配置环境变量，不把密钥写进命令、代码或教程 |
| 模型摘要漏掉 13/25 | 查看确定性 `final-report.json`；摘要检查失败时不替换主结果 |

本实验的完成标准不是“多 Agent 都运行了”，而是普通检索暴露缺口、Agent 补查一次、本地协议留下可读记录、冲突按规则处理，最后没有越过人的决定。
