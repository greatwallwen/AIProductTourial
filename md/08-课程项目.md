# 第七部分　从自己的问题开始

先选一个真实工作时刻，不要先选技术名词。用一页写清角色、对象、当前材料、要做的决定、允许动作、停止条件和观察指标。

接着依次完成：

1. 用 P001—P008 把问题、输入和输出说清楚；
2. 判断哪些步骤需要 Agent，哪些稳定方法值得做成 Skill；
3. 用一个本地数据样本跑通主要动作；
4. 加入检查、次数上限、人工确认和恢复，形成 Loop；
5. 写清角色、状态、不变量、接口和质量场景；
6. 最后再决定是否需要 RAG、MCP、A2A、事件或多个服务。

## CodeBuddy：完成一轮，而不是生成一堆文件

CodeBuddy IDE 是主入口。用 IDE 打开项目，在内置终端运行 `run.bat`，然后从一个案例开始。先看页面，再把该案例的 CodeBuddy Prompt 交给 Agent。不要同时改多个案例，也不要先让它“全面优化”。

下面这段可以放在案例 Prompt 前面。以 B001 为例，换案例时只替换编号和文件名：

```text
你正在 AIProductTourial 中修改案例 B001。

先读取：
1. md/cases/B001-retail-return-evidence.md；
2. dataset/B001-retail-return-evidence；
3. code/cases/B001-retail-return-evidence；
4. code/app/tests 中直接覆盖 B001 的测试。

先用三句话说明：用户此刻要完成什么决定、现有数据能确认什么、
哪些内容不能自动判断。然后按案例中的 CodeBuddy Prompt 实现。

只修改 B001 直接使用的文件。完成后运行该案例的聚焦测试和类型检查，
打开页面走完案例正文规定的主操作；再刷新一次，确认状态仍能解释。
如果测试、控制台或页面有错误，先修正再汇报。

最后只给出：改动文件、测试结果、页面达到的最终状态、仍未验证的事项。
没有新的错误或未满足项就停止。
```

一轮工作有五步：

1. **读**：先读需求、数据字段、已有代码和聚焦测试；
2. **复述**：说明用户决定、可用材料和不能越过的限制；
3. **小改**：一次只改一个案例或一个实验；
4. **检查**：运行聚焦测试、类型检查，并在页面完成一次真实操作；
5. **停**：结果达到案例写明的状态，且没有新错误，就结束这一轮。

## CLI 只做边界清楚的任务

CLI 适合只读分析、聚焦修改或检查。先确认程序和登录状态：

```powershell
codebuddy --version
codebuddy
# 进入交互界面后执行 /status；未登录时执行 /login
```

第一次只让它读文件并给计划：

```powershell
codebuddy -p "读取 B001 的课程段落、数据说明、案例代码和聚焦测试；只输出当前缺口、拟改文件和验收命令，不修改文件。" `
  --permission-mode plan `
  --tools "Read,Glob,Grep" `
  --output-format text
```

需要实施时进入默认权限模式，逐项确认编辑和命令。Agent 申请读取案例之外的目录或运行无关命令时，先拒绝并缩小任务。

当前机器已核对 CodeBuddy CN IDE 与 CodeBuddy Code CLI 的程序入口。CLI 的模型请求因账号未登录而停止，所以课程没有把它写成一次成功的模型回答；[核对记录](../evidence/runtime/codebuddy/receipt.json)保留了这一区别。

代码检查从改动范围开始：

```powershell
Set-Location code
npm.cmd test
npm.cmd run typecheck
npm.cmd run build
```

运行页面后检查控制台、主路径、刷新恢复和错误状态。完成的标准不是页面能打开，而是用户能依靠现有材料走完一次真实决定，系统也知道什么时候不该继续。
