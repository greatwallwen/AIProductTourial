## 1. 本章在全书中的作用

第 1 章已经建立模型的输入—输出边界：模型依据训练形成的模式和本次可见信息生成内容，但不是知识库。本章继续追问“本次可见信息”究竟是什么，以及它为什么既有限又临时。

本章是从“能调用模型”走向“能管理一次调用”的第一步。读者需要理解：

> 程序把哪些信息放进一次调用，模型就在这次调用中看到哪些信息；没有放入的信息不会因为保存在别处就自动可见，调用结束后也不会自动成为长期记忆。

本章在全书中承担四项作用：

1. 解释令牌如何成为模型处理文本、计算窗口容量和核对调用规模的基本计量单位。
2. 固定 Context 的全书定义，防止把上下文、聊天记录、状态、数据库和长期记忆混为一谈。
3. 说明上下文窗口是有限预算，内容更多不必然效果更好。
4. 引入上下文工程的最小方法：为当前任务选择、组织和检查真正需要的信息。

贯穿项目的最小增量是：在第 1 章单次模型调用之前增加一个透明的上下文组装步骤，并记录令牌数量、材料来源、组装顺序和窗口风险。项目仍然只调用模型一次，不增加提示层级、工具、检索、记忆、循环或自动验证。

## 2. 读者已经知道和还不知道的内容

### 2.1 读者已经知道

读者已从第 1 章知道：

- 大语言模型接收输入并生成输出。
- 训练、推理和生成是不同阶段。
- 模型不是可逐条查询、保证来源和自动更新的知识库。
- 模型只能依据训练形成的模式和本次可见信息生成。
- 一次调用成功只证明取得了输出，不证明内容正确。
- 当前贯穿项目能够接收一段文本、调用模型一次并保存原始输出。

### 2.2 读者还不知道

- 文本为什么需要先被切分，以及令牌与字符、汉字、单词为什么不是固定换算关系。
- 什么是上下文，以及一次调用中哪些内容属于上下文。
- 上下文窗口限制的究竟是什么，输入与输出如何共同占用预算。
- 聊天产品为什么看起来“记得”上一轮，以及这种现象为什么不等于模型拥有长期记忆。
- 保存到文件或数据库的信息为什么不会自动进入模型当前上下文。
- 上下文过长、无关、冲突、过时或顺序不当会带来什么问题。
- 如何为一次调用选择和组装最小充分上下文。
- 提示词层级、系统规则、结构化输出、正式验证、RAG、State 和 Memory 的实现。

## 3. 核心问题与学习目标

### 3.1 核心问题

1. 模型接收的文字在进入计算前如何变成可处理的单位？
2. 为什么同一句话在不同模型或分词器中可能占用不同数量的令牌？
3. 本书中的上下文包括什么，不包括什么？
4. 上下文窗口为何是有限预算，超过限制或接近限制时会发生什么？
5. 临时上下文、聊天界面中的历史记录和长期记忆有什么区别？
6. 为什么给模型更多材料有时反而使结果变差？
7. 怎样为贯穿项目组装一份可检查、可复现的单次调用上下文？

### 3.2 学习目标

读完并完成观察实验后，读者应能够：

- 用通俗语言解释 Token、Tokenizer、Token ID、Context 和 Context Window。
- 通过实际分词器而不是固定比例，计算一段输入在指定模型中的令牌数量。
- 准确复述 `codex/GLOSSARY.md` 对 Context 的定义。
- 区分“信息被保存”“信息被程序选中”“信息进入本次上下文”“模型根据它生成输出”四个阶段。
- 说明上下文窗口不是长期记忆容量，也不等于应用可以永久保存的聊天条数。
- 判断一段上下文中的目标信息、必要背景、无关噪声、冲突内容和过时内容。
- 为单次调用建立明确的上下文预算，并为预留输出空间、溢出和空材料设计可观察行为。
- 根据观察实验说明：上下文质量受相关性、位置、冲突和长度共同影响，不能从一次运行推出普遍性能结论。
- 指出当前项目仍缺少稳定规则、结构化输出和独立验证，从而自然进入第 3 章。

## 4. 必须解释及不得提前引入的概念

### 4.1 必须在本章解释

- **令牌（Token）**：模型处理文本时使用的离散单位。令牌可能对应一个字、词的一部分、标点、空白或其他片段，不能简单等同于汉字或英文单词。
- **分词器（Tokenizer）**：按照特定模型的编码规则把输入转换为令牌及编号的组件。
- **Token ID**：分词器为令牌映射的整数编号。编号只在相应词表与编码规则中有意义，不是词义排名。
- **模型相关性**：同一文本在不同模型、版本或分词器中，切分和计数可能不同；不得给出跨模型恒定换算。
- **上下文（Context）**：严格采用 `codex/GLOSSARY.md` 的定义，即一次模型调用时可见的信息集合。
- **上下文来源**：可以包含用户当前输入、程序加入的说明、历史片段和外部提供的材料；“可以包含”不表示本章已经实现所有来源。
- **上下文窗口（Context Window）**：模型一次调用可处理的有限令牌预算。正文必须依据所选接口说明输入和生成输出如何计入限制，不得把所有产品规则写成同一种。
- **输出预留**：组装输入时要为可能生成的输出留下空间；输入刚好未超限不代表调用一定可完成。
- **临时性**：上下文只描述本次调用可见的信息。应用可以再次发送相同材料，但模型不会因为上次看过就自动永久保留。
- **长期记忆的区别**：长期记忆需要外部保存、选择和重新注入机制；本章只解释边界，不实现 Memory，也不展开写入、更新和清理规则。
- **上下文工程（Context Engineering）**：围绕当前任务选择、组织、压缩和检查一次调用所需信息的工程过程。它不等于“把所有资料都塞进去”。
- **上下文噪声**：与当前目标无关、重复、冲突、过时或容易分散判断的信息。本章用可观察结果讨论其影响，不宣称单一固定规律适用于所有模型。

### 4.2 必须明确区分

- Token 与字符、字、单词、字节。
- Context 与训练数据。
- Context 与应用保存的聊天记录。
- Context 与 State：State 是系统显式保存、供后续决策使用的信息；正式定义和实现留到第 8 章。
- Context 与 Memory：Memory 是跨步骤或跨会话保存、检索并重新注入信息的机制；正式分类与治理留到第 12 章。
- Context Window 与数据库容量、文件大小、长期记忆容量。
- Context Engineering 与 Prompt Engineering：前者管理模型本次可见的信息集合，后者组织目标、约束和输出要求；提示部分留到第 3 章。

### 4.3 不得提前系统引入

- 用户提示、系统规则、提示层级、结构化输出和 JSON Schema；属于第 3 章。
- 幻觉分类、不确定性处理、独立验证和评测；属于第 4、14 章。
- 工具调用、API 编排和 MCP；属于第 5、10 章。
- Agent、AI Loop、多步行动和自主决策；属于第 6—7 章。
- State、检查点、恢复和状态腐烂；属于第 8 章。
- RAG、Embedding、向量检索、召回与重排；属于第 9 章。
- Skill、Memory 的实现与治理；属于第 11—12 章。
- 注意力机制公式、位置编码、KV Cache、模型训练细节和推理优化。
- 通过摘要、滑动窗口或检索解决超长上下文的完整架构；可指出后文解决，不在本章实现。

## 5. 章节结构与贯穿案例

### 5.1 章节结构

#### 开场：同一模型为什么“看见的材料不同，回答就不同”

复用第 1 章观察实验中“未提供事实”和“把事实写进输入”的对照。指出变化不是模型自动学会了新事实，而是本次调用可见的信息发生了变化。由此提出两个问题：信息怎样进入模型，以及一次能放多少。

#### 2.1 令牌：模型处理文本的计量单位

- 展示一句简短中文和一句包含数字、标点、英文的混合文本。
- 使用与目标模型匹配的真实分词器显示切分与 Token ID。
- 说明切分依赖模型/编码，不把界面中的视觉字符等同于令牌。
- 说明令牌数量会影响窗口预算、成本和时延，但不在本章做价格横评。
- 明确任何中文或英文换算都只能是特定条件下的粗略估计，实操必须实际计数。

#### 2.2 上下文：模型本次可见的信息集合

- 用“调用包裹”图展示程序如何把不同来源组织成一次输入。
- 说明保存在硬盘、数据库或上一轮界面中的内容，只有被程序再次放入调用才对模型可见。
- 说明模型输出也可以被应用在下一次调用时重新放回上下文，但本章仍只运行一次。
- 用表格区分训练数据、上下文、状态、记忆和外部知识，只解释边界，不展开后四者实现。

#### 2.3 上下文窗口：有限预算，不是永久容量

- 解释窗口限制与令牌计数的关系。
- 说明具体接口可能对输入、输出和其他消息采用不同限制，必须查官方文档。
- 展示“输入预算 + 输出预留 + 安全余量”的计算框架，不给出通用固定比例。
- 覆盖明确溢出、输入被应用截断、输出过早结束三类风险；不能声称所有模型都会自动截断。
- 说明窗口更大只是容量条件，不保证长材料中的每项信息都被同等可靠地使用。

#### 2.4 上下文不等于长期记忆

- 用两次独立调用演示：第一次提供临时代号，第二次不重新提供且关闭历史注入。
- 区分模型、调用程序和聊天产品各自可能保存什么。
- 说明应用保留记录是一种外部持久化行为，只有重新注入才成为新调用的上下文。
- 只给出长期记忆的最小边界，不介绍记忆类型、数据库或检索流程。

#### 2.5 上下文工程：选择与组织，而不是堆满

给出最小工作单：

1. 写清本次任务需要模型知道什么。
2. 标记每段材料的来源、更新时间和用途。
3. 删除无关、重复和明显过时内容。
4. 发现冲突时不静默选择，保留冲突说明或交由人处理。
5. 按任务使用顺序组织材料，并保留清晰分隔。
6. 计算令牌数，为输出留出空间。
7. 保存实际发送的上下文，便于复现观察。

本节不教授第 3 章的提示措辞，也不引入第 9 章的自动检索。

#### 观察实验：逐步增加上下文噪声

使用同一个可核查问题和同一条目标事实，至少设置五组输入：

1. **基线组**：只提供完成任务所需的最小材料。
2. **无关噪声组**：逐批加入主题相近但与答案无关的材料。
3. **重复组**：重复加入同一背景，观察重复是否改变输出。
4. **冲突组**：加入一条明确标注来源和时间的冲突信息。
5. **位置组**：在总内容不变时，将关键事实放在开头、中间和结尾。

控制要求：

- 模型/产品版本、生成设置、任务问题和目标事实保持一致。
- 每组记录实际令牌数量和完整输入，不用字符数代替。
- 每个条件至少重复运行若干次，以观察变化而非依赖一次输出；次数由案例负责人结合成本确定并记录。
- 采用预先写好的简单判定表：是否找到目标事实、是否引用错误信息、是否遗漏限定、输出是否因溢出失败。
- 不把“中间位置一定最差”“更多上下文一定更差”等经验表述写成普遍定律。

#### 小结：模型的临时世界由本次上下文构成

回收令牌、上下文、窗口与长期记忆边界。指出即使材料已经选对，模型仍需要知道目标、规则和输出形式，进入第 3 章。

### 5.2 贯穿案例

第 2 章沿用第 1 章的单次模型调用，不更换主项目：

- **本章前能力**：程序能接收一段文本、调用模型一次并保存原始输出。
- **真实问题**：程序没有记录实际发送了哪些材料、令牌数是否接近窗口，也无法说明为什么某项项目事实对模型可见。
- **最小改动**：增加一个显式的 `context_builder` 或等价模块，从人工指定的材料中组装本次上下文，并在调用前统计令牌。
- **输入**：项目任务、人工选择的必要材料、材料来源和更新时间。
- **输出证据**：实际发送文本、材料清单、令牌计数、窗口上限来源、输出预留、原始模型输出和错误记录。
- **错误路径**：空任务、材料缺失、分词器不匹配、预算超限或服务拒绝时，不静默截断，不自动改写事实；显示原因并停止。
- **人工关口**：人批准材料选择和冲突处理，模型输出仍不自动进入业务系统。
- **本章后能力**：项目能构造并记录一份受预算约束的单次调用上下文。
- **仍然缺少**：稳定的提示规则、结构化输出、事实验证、自动检索、长期记忆、工具和循环。

## 6. 代码、图示和事实核查要求

### 6.1 代码要求

- 在第 1 章一次调用示例上做最小增量，不另起技术栈。
- 使用与实际调用模型匹配的官方或可信分词器；无法匹配时明确标为估算，不得伪装精确。
- 上下文组装代码必须可打印或保存“最终实际发送内容”，避免只展示素材源文件。
- 预算检查至少接收：窗口上限、当前输入令牌数、计划最大输出和安全余量。
- 超限时应在调用前失败并给出可理解的错误；本章不实现自动摘要、检索、截断重试或循环压缩。
- 对材料设置稳定分隔，防止示例中不同来源无边界拼接；不提前讲提示注入安全。
- 至少验证正常材料、空材料、超限材料和分词器配置错误。
- 记录运行环境、依赖版本、模型/编码名称、命令、输入、实际输出和核查日期。
- API 凭据继续使用安全配置，不写入代码或日志。
- 未实际运行的代码必须标注“未验证”。

### 6.2 图示要求

至少包括：

1. **文本到令牌图**：原始文本 → 分词器 → 令牌片段 → Token ID；注明切分随模型/编码变化。
2. **一次调用的上下文边界图**：训练形成的模型、本次上下文、模型输出、模型边界外保存的数据；只画实际可见路径。
3. **窗口预算条**：必要输入、其他材料、输出预留、安全余量共同占用有限窗口。
4. **上下文与长期记忆对照图**：外部保存不等于当前可见，重新注入后才进入下一次上下文。
5. **噪声实验结果表或小型图**：横轴使用实际令牌数或实验条件，纵轴使用预先定义的可观察判定，不以审美评分替代证据。

### 6.3 事实核查要求

- Tokenizer、窗口限制、输入/输出计数规则和接口报错行为必须引用所选模型或服务的官方文档，记录版本与核查日期。
- 不使用“1 Token 固定等于若干汉字/单词”的断言；如给估算范围，必须标明模型、语料和用途限制。
- 不使用未经核实的模型窗口排行榜或“百万级上下文等于多少本书”类营销换算。
- 聊天产品保留历史记录的行为不得归因于模型长期记忆，除非能证明具体注入过程。
- 上下文位置和噪声影响如引用研究，优先引用原始论文，并区分论文条件与本章实验条件。
- 实验数据必须标记模型版本、运行日期、每组次数和生成设置，不能将单次结果概括为稳定规律。
- 合成材料需标记为教学数据；真实项目材料必须脱敏并获得使用授权。
- 旧版 `docs/_source/00-ai-foundations.md` 中的 Token 换算、窗口数字和产品能力不得未经重新核查复用。

## 7. 常见误解与前后章衔接

### 7.1 常见误解

- **“一个 Token 就是一个汉字或英文单词。”** 切分取决于模型和分词器。
- **“Token ID 越大，词越重要。”** ID 是词表映射编号，不表示重要性。
- **“上下文就是用户最后一句话。”** 它是一次调用时模型可见的全部信息集合。
- **“聊天界面显示旧消息，模型就永久记住了。”** 应用可能重新发送历史；显示、保存和注入是不同过程。
- **“文件已经在服务器上，所以模型知道内容。”** 文件只有被读取并放入本次调用才成为上下文。
- **“上下文窗口越大，结果一定越好。”** 容量增加不保证相关性、无冲突或可靠使用。
- **“把所有资料塞进去最保险。”** 无关、重复、冲突和过时信息会增加成本与判断难度。
- **“上下文工程就是提示词工程。”** 两者相关但关注对象不同；提示与规则留到第 3 章。
- **“上下文就是状态或记忆。”** 三者边界不同，正式状态与记忆机制在后文展开。
- **“超限时模型一定会自动处理。”** 有的接口拒绝，有的应用可能截断，必须核查实际行为。

### 7.2 前后章衔接

- **承接第 1 章**：把“本次可见信息”正式定义为 Context，并解释文本如何按 Token 计入有限窗口。
- **衔接第 3 章**：本章解决“放什么、放多少、怎样组织”；第 3 章解决“如何表达目标、规则和输出要求”。
