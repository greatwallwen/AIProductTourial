版本：v0.1

## 1. 本章在全书中的作用

第 1 章说明模型是生成组件，第 2 章说明模型只能依据本次上下文工作。本章解决下一层问题：即使材料已经选对，如果目标、约束和输出形式表达含糊，生成结果仍难以稳定交给程序或人使用。

本章要建立三条全书通用边界：

1. Prompt 是放入上下文的一部分信息，不是模型本身，也不是完整系统。
2. 用户请求与应用规则承担不同职责；规则可以约束输出，但不能创造缺失事实或提供外部执行能力。
3. 结构化输出让程序更容易读取结果，但“格式有效”不等于“内容真实、合理或安全”。

贯穿项目的最小增量是：在第 2 章可记录的单次上下文之上，加入明确的任务模板、应用级规则和一个最小输出结构，并在模型返回后做语法与结构检查。项目仍然只调用模型一次；格式不合格时明确失败，不自动重试，不进入循环，也不把结构检查冒充事实验证。

## 2. 读者已经知道和还不知道的内容

### 2.1 读者已经知道

读者已从第 1—2 章知道：

- 模型接收输入并生成输出，不是知识库或完整任务系统。
- 模型输出流畅不等于事实正确。
- Token 是模型处理文本的单位，计数与模型/分词器相关。
- Context 是一次模型调用时可见的信息集合。
- 上下文窗口有限，需要为输出预留预算。
- 信息被外部保存不等于已进入当前上下文。
- 上下文工程关注为当前任务选择和组织必要信息。
- 当前项目仍是一次模型调用，但已经能够记录实际发送的上下文与令牌预算。

### 2.2 读者还不知道

- Prompt 在 Context 中扮演什么角色。
- 用户提示与系统规则分别由谁提供、解决什么问题。
- 一条清晰提示通常需要哪些信息。
- 规则能约束什么、不能保证什么，以及规则冲突时为什么不能凭想象概括所有平台行为。
- 自然语言输出为什么难以稳定交给程序读取。
- 什么是结构化输出、字段约束、解析和模式检查。
- 格式检查、事实验证和业务验收为什么是不同层次。
- 如何比较模糊、明确和结构化三种提示方式。

## 3. 核心问题与学习目标

### 3.1 核心问题

1. Prompt 与 Context 有什么关系，为什么二者不能互换？
2. 用户提示与系统规则分别表达什么，为什么应用规则不能只依赖用户每次重复输入？
3. 怎样把任务目标、输入、约束和完成形式表达清楚？
4. 好提示能够改善什么，又不能弥补哪些系统缺陷？
5. 为什么“请用 JSON 返回”不等于程序一定能安全解析和使用结果？
6. 结构化输出如何降低接口歧义，又为什么不等于内容已通过验证？
7. 怎样在不增加循环的情况下处理格式错误和规则冲突？

### 3.2 学习目标

读完并完成观察实验后，读者应能够：

- 准确复述 `codex/GLOSSARY.md` 对 Prompt 的定义，并说明 Prompt 是 Context 的一部分。
- 区分用户提示、应用或系统规则、任务材料和模型输出。
- 用“目标、输入、约束、输出要求”四项检查一条任务提示是否完整。
- 把一条模糊请求改写为目标清楚、边界明确、可由人检查的提示。
- 说明系统规则的作用与边界，不把规则写成无法绕过的安全保证。
- 为一个简单任务定义最小结构化输出及字段含义。
- 区分“可解析”“符合结构”“字段内容正确”“任务完成”四种判断。
- 对模糊、明确和结构化三种输入进行受控比较，保留完整提示和原始输出。
- 在贯穿项目中实现一次调用后的解析与结构检查，并在失败时停止而非静默猜测或自动重试。

## 4. 必须解释及不得提前引入的概念

### 4.1 必须在本章解释

- **提示词（Prompt）**：严格采用 `codex/GLOSSARY.md` 定义，即放入上下文、用于描述目标、约束、输入和输出要求的信息。
- **用户提示（User Prompt）**：由用户在当前任务中提供的请求、材料或补充要求。正文需说明具体消息角色和字段名称可能因接口而异。
- **系统规则（System Rule / System Instruction）**：由应用在用户任务之外配置、用于规定模型角色、行为边界和通用要求的信息。若使用具体产品术语，必须以官方文档为准。
- **提示的四个基本部分**：目标、任务输入、约束、输出要求。不是强制模板，但必须作为检查视角。
- **明确性**：可让读者指出对象、范围、限制和完成形式，不能把“写得长”当作“写得好”。
- **规则冲突**：用户要求、应用规则和材料可能不一致；示例必须展示冲突并说明实际优先级依赖接口规范，不能编造通用消息层级。
- **结构化输出（Structured Output）**：按照预先约定的字段、类型和层次组织模型结果，使程序能够解析和检查。
- **模式或结构约束（Schema）**：定义允许字段、必填项、数据类型和必要限制的机器可读约定。正文可使用简化 JSON Schema，但不展开规范全貌。
- **解析（Parsing）**：把输出文本转换为程序可操作的数据结构。
- **语法检查与结构检查**：分别判断文本能否解析、数据是否符合预定字段和类型。
- **格式正确不等于内容正确**：合法 JSON 可以包含错误事实、无效推理或不合业务约束的值。
- **提示的边界**：Prompt 不能让模型自动获得未提供的事实、执行外部行动、拥有长期记忆或保证每次正确。

### 4.2 必须明确区分

- Prompt 与 Context：Prompt 是上下文中的任务与约束信息，不是全部上下文。
- 用户请求与应用规则：来源和职责不同。
- 任务材料与规则：材料中的内容不应自动被当作应用指令；提示注入的安全机制留到第 16 章。
- 自然语言格式要求与机器可检查的 Schema。
- 解析成功、Schema 合格、事实正确、业务可接受和外部任务完成。
- “模型遵循规则的观察结果”与“系统提供强制安全保证”。

### 4.3 不得提前系统引入

- 幻觉分类、不确定性量化、独立验证和评测；属于第 4、14 章。
- Tool、函数调用参数、外部执行和 MCP；属于第 5、10 章。
- Agent、规划、AI Loop、自动修复和多轮重试；属于第 6—7、15 章。
- State、RAG、Skill、Memory；属于第 8—12 章。
- 提示注入攻击、最小权限、数据/指令隔离的安全实现；属于第 16 章。
- 思维链、隐藏推理、提示越狱、元提示、自动提示优化和复杂提示框架。
- 供应商专有的结构化输出协议横评或函数调用机制。
- 用模型生成并执行代码、SQL 或命令。

## 5. 章节结构与贯穿案例

### 5.1 章节结构

#### 开场：材料相同，要求不同，结果为何难以直接使用

沿用贯穿项目中的同一份已选材料，先给出“帮我整理一下”这类模糊请求。展示输出可能有用，却无法判断范围、重点和完成形式。再提出：如果应用要稳定读取结果，任务必须怎样表达？

#### 3.1 Prompt 是上下文中的任务说明

- 回顾 Context，指出材料、任务和规则都可能进入一次调用，但承担不同职责。
- 给出 Prompt 的固定定义。
- 用边界图展示：程序组装上下文，其中包含应用规则、用户提示和任务材料。
- 说明提示不是魔法咒语，不用人格化或“秘诀”叙事。

#### 3.2 用户提示：把当前任务说清楚

用同一任务逐项补齐：

1. 目标：希望模型产出什么。
2. 输入：依据哪些已提供材料。
3. 约束：不得编造缺失字段、长度或范围限制、遇到未知如何表示。
4. 输出要求：人或程序如何读取结果。

强调：

- 明确不等于冗长。
- 示例不要求“模型展示思维过程”。
- 未提供事实时，应允许使用明确的缺失标记，而不是用规则逼模型猜测。

#### 3.3 系统规则：应用级约束与边界

- 说明规则由应用配置，用户通常不应在每次任务中重复承担。
- 使用低风险规则示例，例如“只依据提供材料”“缺失信息标记为 unknown”“不得声称已执行外部动作”。
- 展示一条用户请求与应用规则冲突的情况。
- 若具体接口具有消息优先级，正文必须引用该接口官方文档；通用正文只说明系统需要定义并测试冲突处理。
- 明确自然语言规则可能被忽略、误解或冲突，不能代替程序权限和后续验证。

#### 3.4 好提示的作用与边界

用两列表格说明：

| 可以改善 | 不能保证 |
|---|---|
| 任务范围更清楚 | 缺失事实自动出现 |
| 输出更符合预期形式 | 内容必然真实 |
| 减少不必要歧义 | 每次结果完全相同 |
| 明确未知和拒绝方式 | 外部行动已经执行 |
| 便于人和程序检查 | 安全、权限和业务责任自动解决 |

本节不得写“提示越详细越好”或“万能提示公式”。

#### 3.5 结构化输出：让程序能读，不等于让内容为真

- 从自然语言清单中字段顺序变化的问题引出结构化输出。
- 先定义一个最小对象，例如 `summary`、`missing_information`、`source_items`，字段应服务于贯穿项目。
- 说明字段名称、类型、必填项和未知值表达。
- 展示 JSON 解析与 Schema 检查两个步骤。
- 至少展示三种失败：非 JSON、缺少必填字段、字段类型错误。
- 展示一个格式完全合法但事实错误的例子，为第 4 章埋下问题。
- 格式失败时程序记录错误并停止；本章不自动让模型修复。

#### 观察实验：比较模糊、明确和结构化的三种提示方式

对同一份材料、同一目标、同一模型设置三组：

1. **模糊组**：只给宽泛请求，不指定边界和输出形式。
2. **明确组**：写明目标、输入范围、约束和人可读输出要求。
3. **结构化组**：在明确组基础上加入字段和 Schema。

预先定义观察维度：

- 是否覆盖目标信息。
- 是否遵守输入范围和未知值约定。
- 是否满足长度或数量约束。
- 是否能被程序解析。
- 是否通过 Schema 检查。
- 是否仍含需要事实核对的内容。

实验要求保存每组完整 Prompt、实际 Context、原始输出、解析结果和结构错误。至少重复若干次，次数由案例负责人记录。不得把主观“更像人写的”作为唯一质量指标，也不得从格式合格推出事实正确。

#### 小结：把任务说清，把结果做成可检查接口

回收 Prompt、规则和结构化输出的边界。指出即使结构完全合格，模型仍可能写出错误事实、错误推导或虚假的执行声明，由第 4 章处理。

### 5.2 贯穿案例

- **本章前能力**：项目能组装、记录和计量一次调用的上下文。
- **真实问题**：任务表达仍是临时自然语言，输出形式不稳定，程序无法可靠读取。
- **最小改动**：增加一个版本化但简单的 Prompt 模板、应用规则和最小 Schema。
- **用户输入**：当前任务目标及获准材料。
- **应用规则**：只依据提供材料；缺失信息使用约定标记；不声称已执行外部行动。
- **输出结构**：只包含完成当前文本任务必要的少数字段，不为未来章节预建复杂对象。
- **调用次数**：正常路径只调用模型一次。
- **程序检查**：JSON 解析和 Schema 检查；失败即记录原始输出、错误位置并停止。
- **人工关口**：人仍负责决定内容是否可信和是否采用。
- **本章后能力**：项目能用稳定任务模板发起一次调用，并把合格输出解析为程序数据。
- **仍然缺少**：事实、推理和执行层面的验证；外部工具；自动修复循环；状态和恢复。

## 6. 代码、图示和事实核查要求

### 6.1 代码要求

- 在第 2 章上下文组装代码上做增量，不替换模型或技术栈。
- Prompt 模板必须把规则、用户任务和任务材料明确分开，记录最终发送内容。
- Schema 必须小而明确；字段有用途、类型、必填性和未知值约定。
- 解析与 Schema 检查使用成熟库或标准能力，不手写脆弱的字符串切割。
- 至少覆盖：正常结构、非 JSON、缺字段、类型错误、额外字段策略和空输出。
- 格式错误时停止并显示可定位信息，不静默填字段、不从自由文本猜值、不自动重试。
- 示例输出中不得包含真实密钥、个人信息或未脱敏业务数据。
- 结构化结果不得自动执行命令、写入生产系统或触发高影响动作。
- 记录运行环境、依赖版本、模型/接口版本、完整 Prompt、Schema、原始输出、解析结果和核查日期。
- 若使用供应商原生结构化输出能力，必须同时说明通用概念与供应商特定保证，不能推广到其他接口。
- 未运行示例明确标记，不能把 Schema 定义本身当作验证证据。

### 6.2 图示要求

至少包括：

1. **上下文组成图**：应用规则、用户提示、任务材料共同进入一次 Context；明确 Prompt 是 Context 的一部分。
2. **职责边界图**：用户提供当前任务，应用提供通用规则，模型生成候选输出，程序解析和检查结构。
3. **结构化输出管线**：原始模型输出 → JSON 解析 → Schema 检查 → 合格数据或明确失败；不得画出事实已验证。
4. **三组实验对照表**：完整记录模糊、明确、结构化三组在任务覆盖、约束遵守、可解析性和待核事实上的表现。

### 6.3 事实核查要求

- Prompt、系统消息、开发者消息或结构化输出的具体行为如涉及某接口，必须引用官方文档并记录模型、API 版本和核查日期。
- 不宣称所有模型都采用相同消息优先级、角色名称或 Schema 保证。
- 不使用未经来源支持的“提示技巧可提升百分之多少”等性能数字。
- 观察实验保持模型、材料、任务目标和生成设置一致，并保存完整 Prompt，不能只展示改写后的片段。
- 结构化输出的通过率必须记录样本次数和失败定义，不能只展示成功案例。
- 示例中的项目资料和输出需标明合成或真实；真实数据必须脱敏并授权。
- 不引用厂商营销材料证明提示具有安全保证。
- 旧版素材中的具体平台兼容性、MCP 或 Skill 说法不属于本章，不能直接复用。

## 7. 常见误解与前后章衔接

### 7.1 常见误解

- **“Prompt 就是用户最后输入的一句话。”** Prompt 可以包含目标、约束、输入和输出要求，并可能由不同来源组成。
- **“Prompt 和 Context 是同义词。”** Prompt 是 Context 的一部分。
- **“系统规则永远不会被违反。”** 自然语言规则需要测试，不能替代程序强制边界。
- **“提示越长越专业。”** 质量取决于必要信息是否明确、一致和可检查。
- **“给模型一个角色就能获得专业保证。”** 角色描述不创造资质、事实或责任。
- **“请勿编造就能消除错误。”** 这条规则可能有帮助，但不是事实验证。
- **“JSON 看起来正确就能直接入库。”** 必须解析并检查结构，内容仍需后续验证。
- **“Schema 合格说明答案正确。”** Schema 只约束结构和部分值域。
- **“结构化输出就是工具调用。”** 本章只处理模型返回的数据形式，不执行外部工具。
- **“格式错误时让模型自动改到正确即可。”** 自动修复会形成新的调用和控制问题，留到循环与重试章节。

### 7.2 前后章衔接

- **承接第 2 章**：第 2 章解决一次调用“看见什么”；本章在该 Context 中明确“要做什么、遵守什么、怎样返回”。
- **衔接第 4 章**：本章只能检查语法与结构；第 4 章判断内容是否存在事实、推理或执行错误，并讨论独立验证。
- **为第 5 章留边界**：结构化文本不是外部行动；工具执行由外部程序完成。
- **为第 7、15 章留边界**：格式失败后本章停止，不自动修复或重试。
- **为第 16 章留边界**：规则和材料冲突只作基础观察，提示注入与权限安全后文展开。
- **贯穿项目连续性**：保留第 2 章 Context Builder，只增加 Prompt 模板和结构检查。
