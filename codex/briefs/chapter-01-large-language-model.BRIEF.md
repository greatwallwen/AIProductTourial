## 1. 本章在全书中的作用

本章是第一篇“模型基础”的起点，也是全书贯穿项目第一次接触真实模型的章节。序章已经帮助读者判断什么时候可能需要 AI 循环；本章向内收缩一步，只回答循环中的模型究竟能做什么、不能做什么。

本章需要建立全书后续工程设计的第一条边界：

> 模型接收输入并生成输出；它不是可按事实逐条查询、保证来源、保证时效的知识库，也不负责外部执行、持久化状态或循环控制。

这条边界决定后续章节为什么还需要上下文、提示、验证、工具、状态、外部知识和运行框架。本章不急于补齐这些能力，而是让读者先观察裸模型的一次调用：它可以根据训练中学到的模式生成有用文本，也可能在缺少信息时生成流畅但无法证实的回答。

本章在贯穿项目中的最小增量是：把序章选定的候选任务缩小为一个边界清楚的文本任务，完成一次模型调用，保存输入、原始输出和人工观察记录。项目此时仍不具备工具、循环、状态、检索、记忆或自动验证。

## 2. 读者已经知道和还不知道的内容

### 2.1 读者已经知道

来自已批准的序章任务书，正文应假定读者已经能够：

- 区分“回答问题”和“完成任务”。
- 知道普通程序、单次模型调用、固定工作流、AI 循环和人工主导辅助系统是不同的实现方式。
- 用通俗语言识别 AI 循环中的观察、行动、结果、验证和停止位置。
- 理解模型生成的文字声明不等于外部行动已经执行，也不等于结果已经通过检查。
- 接受“先选择合适的运行方式，再逐层增加能力”的全书路线。

序章不要求读者了解模型内部原理，因此本章不能把这些知识当作已知。

### 2.2 读者还不知道

- 什么是大语言模型，以及“模型”在本书中的准确边界。
- 训练、推理和生成分别发生在什么时候。
- 训练数据与模型生成结果之间是什么关系。
- 为什么模型能回答许多问题，却不能当作可查询、可追溯、持续更新的知识库。
- 为什么模型面对未知、缺失或过时信息时，仍可能给出看似合理的文本。
- 如何完成并观察一次最小模型调用。
- Token、上下文窗口、系统规则、提示设计、结构化输出、幻觉分类和验证方法；这些仍属于后续章节。

## 3. 核心问题与学习目标

### 3.1 核心问题

1. 大语言模型在一次调用中实际做了什么？
2. 训练、推理和生成有什么区别，为什么不能混为一谈？
3. 模型在训练中接触过大量文本，为什么仍不能被当作知识库？
4. 模型能生成流畅内容，是否意味着内容真实、最新、有来源或可直接执行？
5. 当问题需要模型当前看不到的实时事实时，会发生什么？
6. 在贯穿项目只有一次模型调用的阶段，我们能证明什么，又还不能证明什么？

### 3.2 学习目标

读完并完成观察实验后，读者应能够：

- 用通俗语言解释大语言模型、训练、推理和生成，并正确描述三者的先后关系。
- 说明模型在一次调用中是根据当前输入和训练形成的统计模式生成输出，而不是从一个事实表中逐条取回答案。
- 至少从可追溯性、时效性、完整性和正确性四个方面解释“模型不是知识库”。
- 区分“模型可能在训练中见过相关内容”“模型当前能访问某项信息”和“模型生成的说法已被事实证实”。
- 面对一个实时或模型不可见的问题，先判断信息是否在模型当前可见范围内，而不是只评价回答是否流畅。
- 运行一次最小模型调用，保留输入、原始输出、运行环境和人工观察，不把运行成功写成内容正确。
- 指出当前项目版本的能力与局限，并说明第 2 章为什么需要进一步研究模型一次调用时实际能看到什么。

## 4. 必须解释及不得提前引入的概念

### 4.1 必须在本章解释

- **大语言模型（Large Language Model, LLM）**：一种从大量文本中学习语言模式，并根据输入生成输出的机器学习模型。定义应与 `codex/GLOSSARY.md` 中 Model 的边界一致。
- **模型（Model）**：接收输入并生成输出的组件；本章必须明确它不包含外部执行、持久化状态或循环控制器。
- **训练（Training）**：模型从训练样本中调整内部参数、学习统计模式的阶段。只讲目标和结果，不讲矩阵运算、反向传播或训练基础设施。
- **推理（Inference）**：训练完成的模型接收一次输入并计算输出的运行阶段。必须避免把“推理”写成人类式理解或意识。
- **生成（Generation）**：模型在推理阶段逐步产生输出的过程。本章可以说“逐步生成文本单位”，但不得正式讲解 Token、分词或 Token ID。
- **训练数据、内部参数与输出的关系**：模型参数保留从数据中学习到的模式，不等于保存一套可供用户按记录检索的原始资料库。模型可能复现片段，但这不改变它不是知识库的工程边界。
- **知识库**：在本章只作为对比对象，解释为具有显式记录、可查询内容、更新机制和来源边界的数据系统。不要展开数据库或检索架构。
- **当前可见信息**：模型只能依据本次调用实际提供的信息和训练形成的模式生成；这里使用日常语言，不提前定义 Context。
- **信息时效性**：训练发生在调用之前；模型不会因为现实世界发生变化而自动同步更新。具体模型的数据日期必须逐项核查，不能宣称所有模型共享一个固定“知识截止日”。
- **流畅性与真实性的区别**：语言上自然、细节丰富或语气自信，都不是事实正确的证据。
- **模型不知道时的行为**：模型可能拒答、表达不确定、猜测或给出错误细节；具体行为受输入和模型实现影响，不能承诺它总会诚实地说“不知道”。

### 4.2 可以点到但不得展开

- 可以用“输入中提供的信息”说明模型为何能回答某个新事实，但不定义上下文、上下文窗口或长期记忆。
- 可以指出提问方式可能影响回答，但不教授提示词技巧或系统提示。
- 可以指出需要另找证据核对输出，但不讲验证器、评测、独立会话或模型自查。
- 可以指出联网、读取文件或查询系统需要模型外部的能力，但不定义 Tool、API 或 MCP。

### 4.3 不得提前系统引入

- Token、分词器、Token ID、上下文窗口、上下文工程和长期记忆；属于第 2 章。
- 用户提示、系统规则、提示工程和结构化输出；属于第 3 章。
- 幻觉的正式定义与分类、事实/推理/执行错误、模型自查和独立验证；属于第 4 章。
- 工具、函数调用、外部执行、API 和 MCP；属于第 5 章和第 10 章。
- Agent、规划、ReAct、AI 循环代码和自主执行；属于第 6—7 章。
- State、检查点、RAG、向量、Skill 和 Memory；属于第 8—12 章。
- 运行框架、Eval、重试、恢复、权限、安全、可观察性和自主等级；属于第 13—19 章。
- Transformer 结构细节、注意力公式、嵌入、神经网络训练数学、微调方法和模型压缩。
- 通用人工智能、意识、理解力哲学争论、就业预测和模型排行榜。

## 5. 章节结构与贯穿案例

### 5.1 章节结构

#### 开场：回答得像，不等于知道得真

沿用序章的候选项目，展示模型对一个普通问题给出流畅回答，再让它回答一个本次调用中不可见的新事实。两段输出可能同样自然，但证据基础不同。开场只提出问题，不在此处使用“幻觉”等尚未定义的术语下结论。

#### 1.1 模型在系统中的位置

- 重申模型的输入—输出边界。
- 对照序章中的任务系统：模型可以贡献文本或候选判断，但不等于整个系统。
- 用一张边界图分开模型、调用它的程序和现实世界。
- 明确“模型输出了什么”与“外部发生了什么”是两类事实。

#### 1.2 训练：学习模式，不是建立事实目录

- 用同一种语言模式在多种语境中出现的直观例子解释“从样本中学习规律”。
- 说明训练发生在使用之前，结果体现在模型内部参数中。
- 说明训练数据来源、质量和覆盖范围会影响能力，但不展开数据治理。
- 纠正“模型把互联网逐页背进数据库”的误解。
- 同时避免另一个极端：不能说模型只是随机拼词或完全没有保留训练信息。

#### 1.3 推理与生成：一次回答如何出现

- 说明训练完成后，用户使用模型的阶段叫推理。
- 给出“输入 → 模型计算 → 逐步生成输出”的最小过程。
- 说明生成受统计模式影响，输出具有不确定性；不介绍采样参数。
- 明确模型在推理时不会自动重新训练，也不会自动得知现实世界的新变化。

#### 1.4 为什么模型不是知识库

用同一张比较表，从以下方面对照：

| 比较维度 | 大语言模型 | 知识库 |
|---|---|---|
| 主要输出方式 | 根据输入生成内容 | 查询显式记录 |
| 来源定位 | 通常不能从参数中稳定追溯具体来源 | 记录可设计来源字段 |
| 更新方式 | 需要独立的训练、更新或外部信息注入过程 | 可按数据流程新增或修改记录 |
| 正确性 | 流畅输出不保证事实正确 | 仍可能有错误，但可针对记录治理 |
| 完整性 | 不能保证枚举完整 | 可依据数据范围查询和检查 |
| 时效性 | 不会自动同步现实变化 | 取决于更新机制和更新时间 |

表格不得暗示知识库天然正确，也不得暗示模型毫无知识性能力。核心结论是两者的工作方式和工程保证不同。

#### 1.5 能力边界：会生成什么，不代表能保证什么

- 能力面：归纳、改写、概括、起草、分类候选和语言转换等可作为低风险观察示例，但不做跨模型能力排名。
- 边界面：来源、时效、事实正确、完整覆盖、一致输出和外部执行均不能仅由一次模型输出保证。
- 给出使用原则：先判断任务依赖的是语言模式还是明确事实；若依赖事实，先问当前信息从哪里来、如何核对。
- 只提出后续工程问题，不提前给出 RAG、工具或评测方案。

#### 观察实验：让模型回答它不知道的实时问题

实验采用“双证据”设计，避免仅凭模型是否答对一次下结论：

1. **受控不可见事实**：在本地准备一条实验时才生成、未放入模型输入的信息，例如当前项目的一段随机识别码或由实验负责人刚写入记录表的状态值。询问模型该值是什么。
2. **可核查实时事实**：选择一个实验当日可从权威一手来源获得、但未提供给裸模型的问题，例如指定城市的当前观测数据或当天刚发布的公开状态。记录权威来源、查询时间和真实值。
3. 明确关闭或不接入联网检索、文件读取、工具和历史会话；如果所选产品无法确认这些条件，该结果不能作为“裸模型”实验。
4. 原样记录模型回答，不通过改写问题诱导某个预期结果。
5. 将回答拆为“明确承认不可见”“表达不确定”“给出猜测”“给出可核查细节”等可观察行为，不在本章做正式错误分类。
6. 对照真实值后，记录哪些说法有证据、哪些没有证据，以及模型的语气是否影响了读者判断。
7. 改为把真实值明确放进本次输入，再询问同一问题。比较前后差异，只得出“输入可见信息影响输出”的结论，将上下文机制留到第 2 章。

实验不得以一次答对证明模型掌握实时事实，也不得以一次答错证明所有模型在所有问题上都失败。核心观察对象是信息可见性、回答行为和证据，而非厂商胜负。

#### 小结：模型是生成组件，不是事实终点

回收训练—推理—生成关系和模型/知识库差别，列出贯穿项目当前能力与局限。以问题衔接第 2 章：同一个模型为什么在提供不同信息时表现不同，一次调用究竟能看到多少、能保留多久？

### 5.2 贯穿案例

全书贯穿项目尚未由案例负责人正式确定，本任务书不锁定项目领域、模型或供应商。第一章只规定案例增量：

- 输入：序章形成的“实现方式选择记录”和案例负责人批准的一项低风险文本任务。
- 改动：建立最小的单次模型调用入口，接收一段文本输入并原样保存模型输出。
- 观察：记录模型对项目领域内普通语言任务的表现，再询问一项模型当前不可见的项目实时状态。
- 人工关口：人负责触发调用、查看输出、对照真实值和决定是否采用；模型输出不得自动写入业务系统或触发外部行动。
- 交付证据：运行环境、依赖版本、输入、原始输出、错误输出、核查时间和已知局限。
- 本章后的能力：项目能够完成一次模型调用。
- 本章后的局限：没有上下文管理、提示规则、结构化输出、独立验证、工具、循环、状态或恢复能力。

如果贯穿项目仍未批准，可先写案例接口与证据要求，不得用另一个完整项目替代。观察实验中的受控事实只是小型输入，不发展为第二条案例主线。

## 6. 代码、图示和事实核查要求

### 6.1 代码要求

本章允许且建议提供一个最小可运行示例，但代码只能展示一次模型调用：

- 采用中国大陆无需翻墙即可安装依赖并访问的运行环境；具体模型和服务由案例负责人按 `codex/BOOK_CHARTER.md` 选定。
- 把模型调用封装限制在最少必要代码，避免框架样板和供应商特性掩盖输入—输出关系。
- API 密钥必须通过环境变量或安全配置读取，不得写入书稿、仓库、日志或截图。
- 明确记录操作系统、语言版本、依赖版本、安装命令、运行命令、输入和预期的“程序行为”。
- 正常路径只验证“请求成功并获得输出”，不得把它表述为内容正确。
- 至少覆盖缺少凭据、网络或服务调用失败两类错误；本章只清楚显示错误并安全退出，不提前实现重试策略。
- 保存模型原始输出用于观察；不得自动执行输出、修改业务数据或静默美化为“正确答案”。
- 不引入对话历史、上下文裁剪、系统提示、结构化输出、工具调用、循环、状态、检索或记忆。
- 若示例未实际运行，必须标注“未验证”；实际验证由案例负责人记录环境、时间和结果。
- 如果供应商 SDK 使概念变得不清楚，正文应先给供应商无关的伪代码，再把可替换实现放入实操说明。

最小伪代码只能表达：

```text
读取一段输入
调用模型一次
取得并显示原始输出
结束
```

### 6.2 图示要求

至少规划两幅图和一张表：

1. **训练与使用时间线**：训练样本 → 训练 → 已训练模型 → 本次输入 → 推理与生成 → 输出。图中必须显示现实世界可以在训练后继续变化，模型不会因此自动更新。
2. **模型系统边界图**：调用程序把输入交给模型，模型返回输出；模型边界之外单独画出知识库、外部系统和现实世界，不画连接线暗示本章已接入它们。
3. **模型与知识库比较表**：覆盖输出方式、来源定位、更新、正确性、完整性和时效性，并注明两者都可能包含错误。

图示不得：

- 把训练数据画成模型内部可逐条打开的文件柜。
- 把“生成”画成搜索网页或查询数据库。
- 把模型拟人化为拥有意识、意图或人类式记忆的大脑。
- 提前出现 Token、向量、注意力、工具调用、Agent 或循环架构。

### 6.3 事实核查要求

- “大语言模型”“训练”“推理”“生成”等技术说明优先引用教材、原始论文或供应商官方技术文档，避免用营销博客支撑核心定义。
- 如提及具体模型的训练数据日期、知识更新方式、联网能力、版本或接口，必须使用一手来源并记录产品版本、发布日期、核查日期和适用模式。
- 不得给所有模型设置同一个“知识截止日”；也不得把聊天产品的联网、文件读取或记忆能力归因于模型本身。
- 观察实验必须记录是否启用联网、检索、历史会话、文件访问或其他外部能力。无法确认时，应将结论限定为对该产品配置的观察。
- 实时事实必须保存权威来源、获取时间、时区和对照值。易变化的网页结果不能只留截图而无来源信息。
- 不引用无法复现的性能数字，不用单个实验对模型总体能力、模型之间优劣或行业趋势下结论。
- 旧版 `docs/_source/00-ai-foundations.md` 仅作素材库。其 Transformer 历史、Token 换算、模型窗口、产品组织、人物言论和其他时效性表述均不属于本章必需内容，不得未经重新核查移入。
- 不使用“理解”“思考”“记住”“知道”等拟人化词语描述机制；在读者口语或问题标题中使用时，正文必须马上改写为可观察的输入、输出或信息可见性。

## 7. 常见误解与前后章衔接

### 7.1 必须纠正的常见误解

- **“模型训练过大量资料，所以它就是压缩后的知识库。”** 模型学习并编码统计模式，不提供知识库式的逐条查询、来源追踪和更新保证。
- **“模型不是知识库，所以它什么事实都不知道。”** 模型可以生成大量与事实一致的内容，但每次具体输出仍需根据任务风险判断证据要求。
- **“模型只是复制训练原文。”** 输出可能包含复现，也可能组合和生成新表达；本章不把模型简化为复制粘贴系统。
- **“模型只是随机接龙，因此没有实际能力。”** 生成具有统计结构，能够支持许多语言任务；“有能力”与“有事实保证”是两回事。
- **“回答流畅、详细或自信，就说明正确。”** 文风不是证据。
- **“模型答对当前问题，说明它能访问实时世界。”** 可能来自输入、外部产品能力、猜中或已有信息，必须检查实验条件。
- **“模型答错，就是因为知识截止日。”** 信息缺失、问题歧义、生成不稳定或产品配置都可能影响结果；正式错误分类留到第 4 章。
- **“聊天产品拥有的联网、记忆和文件能力都属于模型。”** 本章必须坚持模型与外部系统的边界。
- **“推理就是模型像人一样思考。”** 本章中的推理是运行已训练模型并计算输出的技术阶段。
- **“一次 API 返回成功，说明任务完成且结果可靠。”** 它只证明程序获得了响应。

### 7.2 前后章衔接

- **承接序章**：序章已经决定项目先从单次模型调用开始，并区分模型输出与真实执行；本章解释这个生成组件的基本工作方式和边界。
- **衔接第 2 章**：本章只使用“本次输入中可见的信息”；第 2 章正式解释 Token、上下文、窗口和模型的临时世界。
- **为第 3 章留问题**：本章不优化提问方式；第 3 章再讨论提示、规则和结构化输出如何约束一次生成。
- **为第 4 章留问题**：本章观察到无证据或错误输出，但不做“幻觉”分类，也不教授验证方法。
- **为第 5 章留问题**：本章模型无法自行获取项目实时状态；第 5 章再解释外部程序如何通过工具接触真实世界。
- **为全书主线留证据**：保留第一份原始调用记录，后续章节可在同一任务上逐步加入能力并比较变化。
