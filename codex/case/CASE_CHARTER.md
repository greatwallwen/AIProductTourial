# 贯穿案例章程：电商售后工单处理助手

状态：Approved  
批准日期：2026-07-24  
核查时区：Asia/Shanghai

## 1. 案例定位

全书只维护一个主要实操项目：**电商售后工单处理助手**。

项目从读取一条合成售后工单并完成一次模型调用开始，随着章节推进，逐步增加上下文、规则、结构化输出、验证、工具、循环、状态、外部知识、技能、记忆、运行框架、失败恢复、权限、安全、可观察性和受控自主能力。

最终目标不是制作一个能够随意聊天的“全自动客服”，而是：

> 在合成电商环境中，对售后工单进行事实查询、规则匹配、候选处理、结果验证和受控执行；只有低风险且证据充分的任务可以在明确权限内自动完成，其余任务停止并交给人工。

## 2. 用户、输入与产出

### 主要用户

- 处理售后工单的客服人员。
- 对处理结果、权限和异常负责的客服主管。
- 维护案例运行规则和数据的工程人员。

### 初始输入

- 一条由用户手动提供的合成售后工单文本。
- 示例方向：客户反映商品尚未收到，但订单页面显示已经签收。

### 初始产出

- 模型生成的候选工单摘要。
- 候选摘要只供人工查看，不代表订单、物流或退款事实已经得到确认。

### 第 1 章可运行承诺

第 1 章结束时必须交付读者可以在个人电脑上运行的最小版本，而不是只提供接口说明或伪代码。该版本至少包括：

1. 一份完整、可直接执行的程序。
2. 一条固定的合成售后工单输入。
3. 通过环境变量配置的模型服务地址、模型标识和凭据，不把供应商写死在业务代码中。
4. 面向中国大陆环境的安装与运行命令。
5. 一组不需要真实凭据即可运行的本地程序行为测试；本地测试替身必须明确标注为“不是模型”，不得冒充真实模型输出。
6. 至少一次使用真实模型服务的运行记录；若负责人缺少可用凭据，该项必须明确标记为阻塞或未验证，不能用本地替身代替。
7. 正常响应、缺少凭据、服务失败和调用一次后停止的实际证据。

读者运行真实模型示例时可以从符合本书可达性要求的服务中自行选择。案例可以提供兼容接口的适配方式和多个替代方案，但现阶段不指定唯一供应商。

### 后续产出

后续章节可逐步增加结构化工单、查询结果、处理建议、验证记录、人工审批记录和受控执行结果。未到对应章节前不得提前实现。

## 3. 为什么选择这个案例

- 第 1 章可以从一次低风险文本生成开始，不需要数据库或外部系统。
- 订单、物流和政策事实能够自然引出上下文、工具、检索与验证。
- 售后处理包含明确的步骤、失败和完成条件，适合展示 AI Loop。
- 工单生命周期能够自然引出状态、检查点和失败恢复。
- 查询、回复、修改地址、补发和退款具有不同风险，适合解释最小权限与人工关口。
- 客户文本和检索资料可能包含不可信指令，适合演示提示注入边界。
- 同一任务可以从人工执行逐步演进到限定范围内自主运行。
- 全部业务数据均可合成，避免使用真实客户隐私或真实商业数据。

## 4. 合成数据原则

案例只使用自行设计的合成业务数据，不复制真实客户、订单、物流记录或内部政策。

所有数据必须满足：

1. 人名、联系方式、地址、订单号和客户号均为虚构内容。
2. 域名使用保留测试域名或明确的本地地址。
3. 金额、日期和业务状态为教学目的设计，不影射真实个人或商家。
4. 异常数据必须标注其教学目的，不伪装成真实事故。
5. 数据量保持在读者可以理解、检查和重建的范围内。
6. 权威源数据采用可读、可版本化的文本格式；数据库只能是可重建的派生产物。

计划中的小型数据范围，不是当前已实现承诺：

- 20～30 个订单。
- 8～10 个商品。
- 30～50 条物流事件。
- 10～15 条售后工单。
- 5～8 份售后政策文档。
- 少量订单不存在、物流缺失、状态冲突和恶意指令等受控异常。

实际数据只在相关章节需要时逐步加入，不在第 1 章一次性创建完整数据集。

## 5. 数据载体演进原则

| 章节阶段 | 允许的数据载体 | 引入原因 |
|---|---|---|
| 第 1～4 章 | 可运行程序与直接放入示例的一条或少量合成文本 | 从第 1 章开始动手运行，同时聚焦模型、上下文、输出与验证，不引入数据库 |
| 第 5～8 章 | 小型本地 JSON 文件 | 支持受控查询、循环和状态实验 |
| 第 9～12 章 | JSON 业务记录与 Markdown 政策文档 | 区分业务事实、外部知识、技能和记忆 |
| 第 13 章以后 | 在确有需要时引入可重建的 SQLite 文件 | 支持状态更新、约束、事务和恢复实验 |
| 生产环境讨论 | 通过稳定接口替换本地数据实现 | 讨论迁移边界，不建设完整电商后台 |

SQLite 不是案例的前置条件。若后续引入，合成源数据和初始化程序必须能够从零重建数据库；不得把不可追溯的数据库文件作为唯一事实来源。

## 6. 跨章不变边界

1. 模型输出不等于订单、物流、政策或退款事实。
2. 模型建议某项行动，不等于外部程序已经执行该行动。
3. 查询和写入必须由模型边界之外的程序在授权范围内执行。
4. 未经明确授权，项目不得发送客户回复、修改订单、补发商品或发起退款。
5. 高影响、证据不足、规则冲突和权限不足的工单必须停止并交给人工。
6. 原始输入、模型输出、外部结果和验证结论必须能够区分。
7. API 密钥和其他凭据不得写入代码、数据、书稿、日志或截图。
8. 供应商和模型保持可替换；选用具体服务时另行记录选择标准、中国大陆可用性、核查日期与替代方案。
9. 每章只增加已批准 BRIEF 直接要求的能力，不提前建设完整客服系统。

## 7. 初始工单方向

前几章优先复用同一条合成工单语义：

> 客户表示上周购买的蓝牙耳机尚未收到，但页面显示已经签收；客户周末需要出差，希望了解如何处理。

正式数据尚未创建。后续制作固定样本时，应为相对日期提供明确的基准时间，避免“上周”“周末”在不同运行日期产生不可复现解释。

这条工单可以逐步暴露以下问题：

- 模型可以概括诉求，但不能仅凭工单知道真实物流状态。
- 订单和物流查询需要外部数据。
- 补发、退款或继续等待需要明确政策依据。
- 查询信息与执行退款具有不同权限。
- 最终结果需要区分候选建议、人工批准和真实执行证据。

## 8. 非目标

- 不建设完整电商平台、支付系统、仓储系统或物流网络。
- 不连接真实商家、客户、订单、快递或支付账户。
- 不用单个案例证明某个模型或供应商优于其他选择。
- 不在基础章节讨论微服务、分布式事务或大规模多智能体架构。
- 不把模型自评、自然语言置信语气或“已处理”声明当作客观证据。

## 9. 变更规则

改变案例领域、最终目标、合成数据原则或跨章权限边界属于跨章节变更，需要记录原因并重新获得人工批准。

每章具体增量记录在 `codex/case/chapter-NN.CASE_CHANGE.md`；当前实现和最近验证结果维护在 `codex/case/CASE_STATUS.md`。
