# 第二部分　Agent + Skills：把一次回答变成一件做完的事

Prompt 把工作说清楚，Skill 保存一套可重复的方法，Agent 根据眼前结果决定下一步。

固定步骤已经确定时，用普通工作流：读取文件、计算指标、生成报告、运行检查。只有下一步必须根据中间结果选择时，才需要 Agent。例如，文件格式不确定、不同缺口要调用不同能力、检查失败后要决定补数据还是停止，这些才是 Agent 的工作。

| 能力 | 回答的问题 | 本部分的例子 |
|---|---|---|
| Prompt | 这次要做什么？ | U01—U06 的任务说明 |
| Agent | 现在该选什么、继续还是停？ | S01 的分诊与每节的下一步 |
| Skill | 这类事怎样稳定完成？ | 数据体检、经营简报、机会图、海报、PPTX、小游戏、3D 检查 |
| Loop | 看完结果后怎样再走一轮？ | 下一部分的四类循环 |

在 CodeBuddy 中，直接粘贴每节的 Prompt。Agent 可以读取项目里的 `SKILL.md`、数据和已有文件，再调用对应脚本。课堂只看五件事：

~~~text
输入：看了哪些文件
选择：用了哪个 Skill
作品：生成了什么
检查：作品里哪些数字或动作已经核对
下一步：继续、修改，还是等待人确认
~~~

不要求模型展示长篇思考，只要求把输入、调用、作品、检查结果和下一步说清楚。

本节的数字和文件已经保存在项目中；"交给 CodeBuddy"是重新完成同一任务的课堂入口。

一个 Skill 最小只需要一个目录和 `SKILL.md`。需要稳定计算时加入 `scripts/`，需要规则与样例时加入 `references/`，需要模板或图片时加入 `assets/`。Agent 启动时只看名称和说明，任务匹配后才读完整内容，用到哪个附件再打开哪个附件；这比把所有方法塞进一个超长 Prompt 更省上下文。

```text
skill-name/
├─ SKILL.md       什么时候用、怎样做、怎样检查
├─ scripts/       可重复计算或转换
├─ references/    字段、规则、样例
└─ assets/        模板、图像、字体等静态资源
```

## Skill 先解决"什么时候用"，再解决"怎样做"

一个含糊的名称会让 Agent 见到相似词就误用。`data-profile` 的说明应写明"读取表格并报告结构、范围、重复和缺失"，同时写清它不负责填补、删行和解释业务原因。

| 项目 | 应写清什么 | 例子 |
|---|---|---|
| 触发 | 哪类输入和交付物与它匹配 | 收到 CSV，需要数据体检报告 |
| 不触发 | 哪些相邻任务不属于它 | 用户要预测销量或自动修复缺失值 |
| 必需输入 | 缺什么就不能继续 | 文件路径、允许目录、关键字段 |
| 输出 | 文件、结构和保存位置 | `profile.json` 与 `profile.md` |
| 检查 | 怎样判断本次执行完成 | 行列数可复算，缺失率分母一致 |
| 停止 | 哪些情况应交回给人 | 文件越界、字段缺失、动作越权 |

Skill 的描述用于发现，正文用于执行，脚本用于稳定计算。三者不要互相代替：描述不应塞进完整教程，脚本也不应偷偷扩大 `SKILL.md` 没有授权的动作。

## Skill 也要经过测试、版本和安全检查

发布前至少检查四类问题：

1. 用一个应触发任务和一个不应触发任务检查路由；
2. 用固定样本核对输出字段、数字和失败状态；
3. 检查脚本是否联网、写出允许目录或执行未声明命令；
4. 修改输出合同或权限时提升版本，并让旧样本重新运行。

团队可以把 Skill 状态保持为"草稿、复核、可用、停用"四种。停用不是删除历史文件，而是停止新任务发现它，并保留旧结果可以追溯。来自外部仓库的 Skill 先读说明和脚本，再决定是否安装；Star 数、作者名气和一段漂亮示例都不能替代本地检查。

## Skill 怎样从零搭起来：先 SOP，再分层迭代

前面讲了 Skill 的最小结构和发布前检查。但一个 Skill 不是一上来就能写好的——直接让 AI 写 Skill，往往得到通篇"保证质量""合理安排步骤"的空话。正确顺序是先梳理人工 SOP，再压缩成 Skill。

### 先写人工 SOP，再压缩成 Skill

以 S02 数据体检为例，人工 SOP 是：收到 CSV → 确认文件路径在允许目录 → 完整读取不抽样 → 逐字段统计行列数/重复/缺失 → 缺失率分母与总行数一致 → 生成 JSON 和 Markdown → 遇到越界或字段缺失就停。梳理完这条 SOP 后，筛选出三类内容：

| 内容类型 | 处理方式 | S02 中的例子 |
|---|---|---|
| 每次必做的固定步骤 | 写入 SKILL.md 主流程 | 完整扫描、逐字段统计、生成 JSON+MD |
| 视情况调整的弹性环节 | 写入 references/ 供按需查阅 | 不同数据集的字段含义差异 |
| 可模板化的重复内容 | 写入 assets/ 或 scripts/ | profile.json 的固定结构、缺失率计算脚本 |

只把最稳定、最高频、可复用的内容写入 SKILL.md；弹性内容和模板素材各归其位。这与"先解决什么时候用，再解决怎样做"衔接：SOP 梳理时就要先定触发条件（收到 CSV 需要数据体检报告）和不触发条件（用户要预测销量或自动修复缺失值）。

### 两种搭建方式，按需选择

**方法一：边做边记，手动搭建。** 从最近要落地的真实任务入手，让 Agent 完整做完一次，逐步复盘三个问题：哪一步必须手动补充信息？哪一步信息不足就会出错或瞎编？哪一步是纯机械重复、无需思考？真实复盘总结的内容才值得写入 Skill，能避免"文档看着完整、实际完全用不上"。本仓库 S01—S08 都是这样从真实任务中沉淀出来的。

**方法二：用 Skill Creator 快速生成初稿。** 前提是你自己已经想清楚完整流程。填空模板如下：

```text
## 任务
帮我创建一个 Skill，名称为【Skill 名】，核心用途是【具体可落地的任务】。

## 触发
当我提及【关键词1】、【关键词2】、【关键词3】时，自动触发该 Skill。

## 流程
完整执行步骤：
1.【第一步具体操作】
2.【第二步具体操作】
3.【第三步具体操作】......

## 要求
【必填规则、禁用操作、所需工具、注意事项等】

## 输出
【固定输出格式：Markdown/HTML、固定结构、排版标准】

## 补充
【其他辅助说明】

请先完成三项校验：
1. 分析当前信息是否充足、能否落地
2. 缺失信息通过提问让我补充完整
3. 信息确认无误后，再生成最终 Skill
```

两种方式不互斥：先用方法二生成骨架，再用方法一在真实任务中迭代补全，是常见路径。

### 分层迭代：主文件只留核心

Skill 越用越乱的根因是主文件臃肿——图片出错加一条规则、文案缺截图补一条说明、流程出问题加一个补丁，最终核心流程、历史问题、临时规则、工具说明全部挤在 SKILL.md 里。黄金迭代原则是：SKILL.md 只留核心流程和不变规则，所有细节全部拆分。

| 内容类型 | 存放位置 |
|---|---|
| 核心流程、永久不变规则 | 保留在 SKILL.md |
| 详细规则、参考案例、历史复盘 | 放入 references/ |
| 文章模板、配图素材、配色方案 | 放入 assets/ |

后续新增任何规则或内容，先判定归属：主流程、参考资料、模板素材、自动化脚本，对号入座。本仓库的 `skill_lint.mjs`（见第 13 章）会检查六槽结构完整性，缺一格就报 MED——结构完整不是靠人记，而是靠门禁守。

### 用真实任务验收

文档排版再规整、结构再清晰，不代表 Agent 执行能稳定落地。改完 Skill 后用三类真实历史任务闭环验收：

1. **信息完整任务**：测试能否按标准流程完整执行、交付达标。
2. **信息缺失任务**：测试能否主动识别关键缺失信息、主动提问补全，而不是瞎编。
3. **不匹配任务**：测试能否精准识别场景不属于自己、及时终止而不强行执行。

每次只改一个点位，用同一批任务复测，精准定位优化效果。这与前面"发布前检查四类"互补：一个是检查维度（路由/输出/脚本/版本），一个是任务维度（完整/缺失/不匹配）。

### 合格 Skill 的四个问题

一个合格、好用的 Skill，打开必须能回答四个问题：

- 它专门解决什么问题？
- 标准执行第一步是什么？
- 遇到特殊情况去哪里查规则？
- 最终交付的成果标准是什么？

答不上任何一个，这个 Skill 还不能算"可用"。

> 参考：米果AI研究室《别再瞎堆提示词了，这才是 Skill 的正确用法》（2026-08-07），本节将其"先 SOP 再 Skill / 两种搭建方式 / 分层迭代 / 真实任务验收 / 合格四问"的方法论融入本仓库的 Skill 工程体系。

## S01　先分诊，再动手

### 场景

"帮我处理数据"可能只是查看 CSV，也可能夹着删除源文件的要求。Agent 不能靠关键词立刻执行；它要先检查输入是否齐全、动作是否被允许。

### 交给 CodeBuddy

~~~text
在当前 Course_AIProduct 项目中完成一次能力分诊，不要执行后续任务。

读取 code/skills/capability-router/SKILL.md，
以及 code/skills/capability-router/examples/ 下的五张任务卡。

对每张任务卡只返回：
1. task_id；
2. selected 或 blocked；
3. 选择的最小 Skill；
4. 一句可公开的选择理由；
5. 缺少的输入或停止原因。

只能选择项目能力清单中的本地 Skill。
缺少必要输入时停止；请求删除源文件、联网或执行任意命令时，
不得自行扩大权限。不要输出隐藏推理过程。
~~~

### 五张任务卡的分诊结果

下面五个决定来自项目里的分诊规则。缺输入或动作越权时，结果就是停止。

| 任务 | 决定 | 原因 |
|---|---|---|
| 检查 CSV | 选择 data-profile | 文件路径和只读权限齐全 |
| 做会员发券实验简报 | 选择 metric-brief | 已给 CSV、8 元券和目标分层 |
| 只有一句"画机会图" | 停止 | 缺少 csv_path |
| 分析后删除源文件 | 停止 | delete_source 未获授权 |
| 把门店记录整理成机会图 | 选择 product-opportunity-map | 输入和输出范围清楚 |

### 这五个决定说明什么

五张任务卡中，三张进入下一步，两张停下。分诊规则没有为缺失文件猜路径，也没有为了完成任务擅自删除源文件。

### 为什么"停下"也是正确结果

Agent 的价值不是每次都找到一个工具，而是区分"现在能做"和"现在必须停"。一句选择理由就够公开说明，不需要展示冗长的内心独白。

> S01分诊体现了逻辑边界守护：先检查输入齐全与动作允许，缺输入或越权时停止。Agent不是万能的——证据不足时悬置判断，高影响动作交给人，不可判定时停下。分诊表里两个"停止"不是失败，而是逻辑边界守护的正确落地。

## S02　别急着分析：先给 21,039 行数据做体检

### 场景

U04 的语言模型已经把问题缩小，却把两个空值率算错了 0.01 个百分点。现在不再让模型估算，而是完整读取文件。

### 交给 CodeBuddy

~~~text
先浏览 code/skills 下各 SKILL.md 的名称和用途，
选择能完成下面任务的最小 Skill，再阅读它的完整说明：
对 dataset/06-beijing-air-quality-audit/case.csv 做只读数据体检。

完整扫描文件，给出行列数、时间范围、完全重复行，
以及 PM2.5、PM10、SO2、NO2、CO、O3 六项污染物的缺失数和缺失率。

不得修改源文件，不得自动填补、删行或解释污染成因。
把结果保存为 `profile.json` 和便于阅读的 `profile.md`。
若文件越出 dataset 目录、格式不符或必需字段不存在，停止并说明缺什么。
~~~

### 数据体检记录

| 项目 | 内容 |

| 选择 | [`data-profile`](../code/skills/data-profile/SKILL.md)，因为分析前还没确认数据质量 |
| 执行 | 只读完整扫描，生成 JSON 和 Markdown |
| 观察 | 21,039 行、21 列、完全重复 0 行 |
| 决定 | 数据可以继续使用，但不能擅自决定怎样处理空值 |

### 六项缺失率

| 字段 | 缺失数 | 缺失率 |
|---|---:|---:|
| CO | 1,027 | 4.88% |
| O3 | 830 | 3.95% |
| NO2 | 656 | 3.12% |
| PM2.5 | 466 | 2.21% |
| SO2 | 417 | 1.98% |
| PM10 | 334 | 1.59% |

完整结果可打开查看：[数据体检](../evidence/runtime/agent-skills/S02/profile.md)。

### 为什么计算交给 Skill

模型负责决定检查什么，确定性 Skill 负责计数。空值不是零，发现空值也不等于可以自动填补或删行；处理方法要等业务口径明确后再定。

> S02数据体检需要全集/子集辨析：21,039行空气质量数据是全集，但12个站点是子集。全场缺失率4.88%不等于每个站点都缺4.88%——聚合指标可能掩盖子集差异。体检报告要同时给出全场口径和分组口径，避免辛普森悖论。

## S03　一张 8 元优惠券，先发给谁？

### 场景

会员表有行为计数和课程派生分层，没有交易金额，也没有绝对事件时间。它能支持一次小规模发券实验设计，却不能回答收入、复购周期或 ROI。

### 交给 CodeBuddy

~~~text
先浏览 code/skills 下各 SKILL.md 的名称和用途，
选择能完成下面任务的最小 Skill，再阅读它的完整说明：
使用 dataset/02-member-value-experiment/case.csv，
为"成长"分层设计一次每人8元优惠券的小规模实验简报。

先检查必需字段是否齐全，再输出事实、解释、下一步和不能计算的指标。
所有数字必须带筛选条件或公式。
优惠券金额是实验参数，不是历史支出；
面额上限不是核销成本，也不是收入。

把计算结果保存为 `metrics.json`，把经营说明保存为 `business-brief.md`。
源表缺少交易金额或绝对时间时，明确写"不可计算"，
不得补造ROI、客单价、历史收入或复购周期。
~~~

### 本地简报计算

按任务目标，本地运行使用 [`metric-brief`](../code/skills/metric-brief/SKILL.md)：它需要从已经允许读取的会员 CSV 计算指标，并生成一页经营简报；不需要图片、网页或文档导出能力。

| 项目 | 结果 |
|---|---:|
| 会员数 | COUNT(DISTINCT user_id) = 5,000 |
| "成长"分层 | 1,250 人；1,250 ÷ 5,000 = 25.00% |
| 全体人均购买次数代理 | SUM(有效 buy_count) ÷ COUNT(有效 buy_count) = 8.5866 |
| "成长"分层人均购买次数代理 | 筛选 value_segment=成长 后，同式计算 = 7.4712 |
| 每人 8 元的名义面额上限 | 10,000 元 |

### 简报怎样说

[经营简报](../evidence/runtime/agent-skills/S03/business-brief.md)把四种内容分开：

> 事实：1,250 × 8 元 = 10,000 元。  
> 解释："成长"分层只是候选实验对象。  
> 下一步：在分层内随机分实验组和对照组。  
> 不能计算：历史收入、客单价、复购周期和 ROI。

### 为什么要保留"不可计算"

一个好 Skill 不只会产出数字，还会保留"算不出来"的格子。如果要求"证明发券会提高收入"，Agent 应把它改成待验证假设，而不是帮用户补出因果结论。

## S04　店长的一句抱怨，究竟是不是功能需求？

### 场景

店长说："差评来时不知道先找订单、先回复还是先问区域经理。"如果直接问"应该做什么功能"，很容易得到一个空泛的 AI 助手。

### 交给 CodeBuddy

~~~text
先浏览 code/skills 下各 SKILL.md 的名称和用途，
选择能完成下面任务的最小 Skill，再阅读它的完整说明：
只使用 dataset/S-agent-skill-cases/case.csv 中 S04 的四条课程记录。

把店长原话、问题、机会和首个实验整理成机会图。
每个节点必须保留 source_refs 和 rule_id。

不要把"做一个AI按钮"当成用户需求；
不得发明受访者数量、问题发生率、市场规模或因果效果。

输出 `opportunity-map.json` 和可编辑的 `opportunity-map.svg`。
~~~

### 从原话到首个实验

按任务目标，本地运行使用 [`product-opportunity-map`](../code/skills/product-opportunity-map/SKILL.md)，因为输入是带来源位置的流程记录，交付物是可编辑机会图，而不是一篇产品建议。

| 从哪里来 | 变成什么 |
|---|---|
| 店长原话 | 差评处理时的决策困难 |
| 课程记录中的动作 | 缩短订单定位、缩短审批等待 |
| 课程记录中的检查项 | 先看订单关联能否把平均定位时间降到 3 分钟 |

输入是四条课程记录，不是四位真实受访者。输出有五个节点和五条关系，每个节点都能回到原句。

### 为什么先画机会而不是功能

先从原话走到可以验证的问题，再谈解决方案。缺少原话或来源位置时就不补节点；想改图，先改输入或规则，而不是直接在图上把假设画成事实。

## S05　雨天旧书店：三套方向，选一套生成

### 场景

创意简报只有一句主题还不够。画面需要受众、标题、必备文字、可见主体和禁用项，否则所谓"三套方向"常常只是同一张图换颜色。

## S09　把静态流程图变成会走的动画：Archify + 录屏

### 场景

案例库里每个 B 案例都有两张 SVG：`*-requirement.svg`（需求流程）和 `*-architecture.svg`（技术架构）。静态图能看懂结构，但看不出"谁先动、数据往哪流、哪一步是关键判断"。把静态 SVG 变成会按 trace 顺序逐节点点亮的动画视频，读者一眼就能看到流程方向和重点步骤。

### 原静态图

![B01 需求流程](../assets/case-diagrams/B01-requirement.svg) 

![B01 技术架构](../assets/case-diagrams/B01-architecture.svg) 

### 交给 CodeBuddy

~~~text
把 assets/case-diagrams/B01-requirement.svg 和 B01-architecture.svg
变成带 trace 动画的 webm 视频。

第一步：用 archify-main skill 的 render 命令，把案例 JSON IR 渲染成
  交互式 HTML（含 trace 动画、play/replay 按钮、showAll 复位）。
  - 需求流程用 diagram_type=workflow
  - 技术架构用 diagram_type=architecture
  - meta.animation = trace

第二步：用 puppeteer 打开 HTML（?present=1），按 15fps 截帧。
  - 先移除 data-wide-diagram 属性（否则 SVG 固定 720px 只占左上角）
  - 需求流程：用 getCTM()+getBBox() 计算所有节点实际边界，重设 viewBox 让内容占满
  - 技术架构：不调 viewBox，用页面原始 1600×900 尺寸
  - 触发 play，监测按钮文本变成 "Replay"（动画播完）
  - 检测到 Replay 后调用 showAll 复位视图，再截 1 秒尾帧后停止
  - 用 ffmpeg 把帧序列编码为 webm（libvpx-vp9, 500k, yuva420p）

输出：assets/case-diagrams/B01-requirement.webm 和 B01-architecture.webm
~~~

### 三步管线

| 步骤 | 脚本 | 输入 → 输出 |
|---|---|---|
| 1. 生成 JSON IR | `gen-json.mjs` | 案例数据 → `B01-*.json`（节点、边、泳道、阶段） |
| 2. 渲染交互 HTML | `deliver-all.mjs` 调 `archify render` | `B01-*.json` → `B01-*.html`（含 trace 动画） |
| 3. 录屏编码 webm | `make-webm.mjs` 调 puppeteer + ffmpeg | `B01-*.html` → `B01-*.webm` |

三个脚本都在 `assets/case-diagrams/gif-work/` 下。archify-main skill 负责第二步——把 JSON IR 变成可交互、可播放的 HTML；第一步和第三步是围绕它的"喂料"和"收尾"。

### 实际踩坑与调整

录屏不是"打开就截"那么简单，实际遇到三个问题：

| 问题 | 原因 | 解决 |
|---|---|---|
| 需求流程图只占左上角 | `data-wide-diagram` 把 SVG 固定 720px | 移除该属性 + 用 `getCTM()`/`getBBox()` 重算 viewBox |
| 技术架构图被裁切 | 调了 viewBox 反而破坏原始布局 | 不调 viewBox，用页面原始 1600×900 |
| 视频太长（8-10 秒） | 固定截帧数，不管动画是否播完 | 动态检测 "Replay" 文本 → 调 `showAll` → 等 1 秒停 |

### 为什么用 Skill 而不是直接手写动画

手写 SVG 动画要逐节点算 `stroke-dasharray`、逐边写 `<animate>`，20 个案例 × 2 张 = 40 张图，维护成本高且风格难统一。archify-main skill 把"JSON IR → 交互 HTML"这一层固化下来：节点、边、泳道、阶段、trace 顺序都由 JSON 描述，渲染逻辑由 skill 的模板统一控制。换案例只需换 JSON，不动渲染代码。

录屏脚本（`make-webm.mjs`）解决的是另一个问题：archify 产出的是 HTML，案例 md 里嵌的是 webm。puppeteer 负责把"可交互"变成"可播放"——自动 play、检测 Replay、showAll 复位、截帧、ffmpeg 编码，整条链不需要人按按钮。

### 怎样复用到其他案例

```text
# 1. 生成 JSON IR（改 gen-json.mjs 里的案例参数）
node gen-json.mjs

# 2. 用 archify 渲染 HTML
node deliver-all.mjs

# 3. 录屏编码 webm（改 make-webm.mjs 的 targets 数组）
node make-webm.mjs
```

`deliver-all.mjs` 的 `files` 数组和 `make-webm.mjs` 的 `targets` 数组里加一行 `B02-*`，就能对 B02 重复同样的流程。B01-B20 共 40 张图，同一套管线批量产出。

## A01　一次查不够时，Agent 怎样补查、交接并停下来

### 场景

地铁压缩机的五分钟窗口有 25 条公开传感记录，其中 13 条被课程数据标为已知故障区间。问题故意问得很危险："这是否足以判定故障并自动停机？"数据可以回答窗口里发生了什么，却没有设备身份、现场观察、维修结果和控制权限。

本实验使用 [`case.csv`](../dataset/09-metro-agentic-rag/case.csv) 与四条 [`knowledge.jsonl`](../dataset/09-metro-agentic-rag/knowledge.jsonl)：两条说明公开数据和字段，两条说明课程检查程序和人工批准规则。

### 先看普通 RAG 少了什么

普通 RAG 只做一次检索，范围限定为 `DATA-09`，取回字段说明和数据来源：

| 已拿到 | 仍缺少 | 此时能回答什么 |
|---|---|---|
| TP2、TP3、油温、电流的字段说明；公开数据来源 | 检查程序、批准规则、允许动作 | 只能描述窗口，不能回答是否可以停机 |

它没有答错，但任务没有做完。问题不在于再写一段更强硬的 Prompt，而在于先检查资料是否覆盖了"数据事实"和"行动规则"。

### 交给 CodeBuddy

~~~text
运行 code/labs/advanced-agent-lab 中的高级 Agent 实验。
问题是：五分钟传感窗口是否足以判定压缩机故障并自动停机？

先用普通 RAG 只查 DATA-09，一次检索后记录仍缺什么。
再运行 Agentic RAG：检查是否同时拿到 DATA-09 和 COURSE-POLICY-09；
缺少策略时改写查询并补查一次，资料齐全后停止检索。

通过本地 MCP 完成 initialize、tools/list 和 tools/call；
把窗口复核、运营响应和权限复核分别交给三个 A2A Agent，
保存 Message、Task 与 Artifact。若意见冲突，必须引用规则再决定采用哪条。

禁止诊断故障、自动停机、维修或调用设备控制工具。
最终只能整理现场检查申请，并停在有权限的主管决定。
先离线重放；若机器已配置阿里模型密钥环境变量，再让 qwen-plus
把确定性结果压缩成四行，并检查"25条中13条标记"和"等待人工决定"没有丢失。
~~~

### Agentic RAG 多做了哪一步

Agent 第一次检索后发现只有 `DATA-09`，于是把问题改成"检查工单是否需要人工批准，是否允许自动停机或维修"，再查 `COURSE-POLICY-09`。第二次检索拿到检查程序与批准规则，随即停止。

| 比较 | 普通 RAG | Agentic RAG |
|---|---|---|
| 查询次数 | 1 | 2 |
| 来源 | 公开数据与字段 | 公开数据、字段、检查程序、批准规则 |
| 自检 | 无 | 检查两类来源是否齐全 |
| 结果 | 资料不足 | 可以整理检查申请 |
| 最后状态 | 未完成 | 等待人工决定 |

这里的"Agentic"不是检索次数多，而是它会检查缺口、改变检索范围，并在条件满足后停下。

### MCP 连接了什么

本地客户端通过 stdio 启动只读服务器，按 `2025-11-25` 完成初始化和能力协商。服务器只暴露两个工具：

| 工具 | 允许输入 | 不允许什么 |
|---|---|---|
| `search_knowledge` | 查询、`DATA-09` / `COURSE-POLICY-09`、1～5 条 | 任意目录、未知来源、互联网补查 |
| `read_sensor_window` | 固定切片、起止时间、四个传感字段 | 任意文件、密码字段、设备命令 |

本轮实际记录到 `initialize`、`notifications/initialized`、`tools/list` 和三次 `tools/call`。完整消息在 [MCP 记录](../evidence/runtime/advanced-agent-lab/qwen-plus/mcp-transcript.json) 中。

### A2A 为什么不是三个本地函数

窗口复核、运营响应和权限复核分别带有自己的 Agent Card。主 Agent 向每个角色发送 Message；角色返回状态为 `completed` 的 Task，并把意见作为 Artifact 交回。三份意见可以独立检查，也可以来自不同部署，交接结构不依赖它们内部怎样实现。

| 角色 | 建议 | 引用 | 汇总时怎样处理 |
|---|---|---|---|
| 传感窗口复核 | 创建检查申请 | 数据来源、字段说明 | 保留 |
| 运营响应 | 立即停机 | 只有数据来源 | 缺权限规则，驳回 |
| 权限复核 | 等待人工批准 | 检查程序、批准规则 | 保留 |

冲突不是投票解决。`COURSE-09-APPROVAL` 明确禁止自动停机，而公开传感数据也不提供诊断或控制权限，因此汇总结果选择"准备检查申请"，状态保持"等待人工"。三份任务和产物见 [A2A 交接记录](../evidence/runtime/advanced-agent-lab/qwen-plus/a2a-tasks.json)。

### 出了问题怎么查

| 现象 | 先查什么 |
|---|---|
| `MCP session is not initialized` | 客户端是否在 `tools/list` 前发送了 `initialize` 和 `notifications/initialized` |
| 普通 RAG 直接给停机结论 | 检索结果是否只有 `DATA-09`，回答是否擅自补了权限 |
| Agent 不断重复检索 | 是否写明两类必需来源和"资料齐全后停止" |
| 三个角色都给同一种答案 | Agent Card 是否真的分开岗位责任，还是只换了名称 |
| 实时模式显示 `authentication_missing` | 按实验 README 配置环境变量，不把密钥写进命令、代码或教程 |
| 模型摘要漏掉 13/25 | 查看确定性 `final-report.json`；摘要检查失败时不替换主结果 |

本实验的完成标准不是"多 Agent 都运行了"，而是普通检索暴露缺口、Agent 补查一次、本地协议留下可读记录、冲突按规则处理，最后没有越过人的决定。
