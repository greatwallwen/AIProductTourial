# 第七部分　从自己的问题开始

先选一个真实工作时刻，不要先选技术名词。写下一页内容：角色、对象、当前材料、要做的决定、允许动作、停止条件和观察指标。

接着依次完成：

1. 用 U01—U06 把问题和输出说清楚；
2. 判断哪些步骤需要 Agent，哪些方法值得做成 Skill；
3. 用一个本地数据样本跑通主要动作；
4. 加入检查、次数上限、人工确认和恢复，形成 Loop；
5. 最后再决定是否需要 RAG、MCP、A2A 或多个 Agent。

## Skill 的两种搭建方式

第 2 步"判断哪些方法值得做成 Skill"之后，怎样把方法真正写成 Skill？有两种方式：

**方法一：边做边记。** 从最近要落地的真实任务入手，让 Agent 完整做完一次，逐步复盘——哪一步必须手动补充信息、哪一步信息不足就会出错、哪一步是纯机械重复。真实复盘总结的内容才值得写入 Skill。本仓库 S01—S08 都是这样沉淀的。

**方法二：用 Skill Creator 快速生成初稿。** 前提是你已经想清楚完整流程。填空模板见 [03 章 · Skill 怎样从零搭起来](03-Agent与Skill工程.md#skill-怎样从零搭起来先-sop再分层迭代)。

两种方式不互斥：先用方法二生成骨架，再用方法一在真实任务中迭代补全。详细方法论（先 SOP 再 Skill、分层迭代、真实任务验收、合格四问）见 [03 章](03-Agent与Skill工程.md)。

## CodeBuddy：完成一轮，而不是生成一堆文件

CodeBuddy IDE 是主入口。用 IDE 打开 `Course_AIProduct` 文件夹，在内置终端运行 `run.bat`，然后从一个案例开始。先看页面，再把该案例的 CodeBuddy Prompt 交给 Agent。不要同时改二十个案例，也不要先让它“全面优化”。

下面这段可以直接放在案例 Prompt 前面。以 B01 为例，换案例时只替换编号和目录：

```text
你正在 Course_AIProduct 中修改案例 B01。

先读取：
1. md/chapters/06-business-cases.md 中 B01 的需求、数据、操作和结果；
2. dataset/01-retail-return-evidence；
3. code/cases/01-retail-return-evidence；
4. code/app/tests/case-01-return-evidence.test.tsx。

先用三句话说明：用户此刻要完成什么决定、现有数据能确认什么、哪些内容不能自动判断。然后按案例 Prompt 实现。

只修改 B01 直接使用的文件。完成后运行该案例的聚焦测试和类型检查，打开页面走完一次“创建补证任务—材料回传—提交独立复核”。如果测试、控制台或页面有错误，先修正再汇报。

最后只给出：改动文件、测试结果、页面达到的最终状态、仍未验证的事项。没有新的错误或未满足项就停止。
```

一轮工作有五步：

1. **读**：让 Agent 先读需求、数据字段、已有代码和聚焦测试。
2. **说清楚**：要求它先复述用户决定、可用材料和不能越过的限制。
3. **做小改动**：一次只改一个案例或一个实验，不顺手整理无关目录。
4. **当场检查**：运行聚焦测试、类型检查，并在页面完成一次真实操作。
5. **停**：结果达到案例写明的状态，且没有新的错误，就结束这一轮。

### CLI 只做窄任务

CLI 适合重复执行只读分析、聚焦修改或检查。先确认程序和登录状态：

```powershell
codebuddy --version
codebuddy
# 进入交互界面后执行 /status；未登录时执行 /login
```

第一次只让它读文件并给计划，不允许工具范围扩张：

```powershell
codebuddy -p "读取 B01 的课程段落、数据说明、案例代码和聚焦测试；只输出当前缺口、拟改文件和验收命令，不修改文件。" `
  --permission-mode plan `
  --tools "Read,Glob,Grep" `
  --output-format text
```

需要实施时进入默认权限模式，逐项确认编辑和命令。课程不使用跳过权限模式；Agent 申请读取案例之外的目录或运行无关命令时，先拒绝并缩小任务。

当前机器已核对 CodeBuddy CN IDE 与 CodeBuddy Code CLI 的程序入口。CLI 的模型请求因账号未登录而停止，所以课程没有把它写成一次成功的模型回答；[核对记录](../runtime/codebuddy/receipt.json)保留了这一区别。

代码检查从改动范围开始：

```powershell
cd Course_AIProduct\code
npm test
npm run typecheck
npm run build
```

运行页面后检查控制台、主路径、刷新恢复和错误状态。完成的标准不是页面能打开，而是用户能依靠现有材料走完一次真实决定，系统也知道什么时候不该继续。

## 面对复杂问题的逻辑三步法

从自己的问题开始时，可以用逻辑三步法结构化拆解：

1. **命题化**：把"我想做一个AI产品"变成可验证的命题——角色是谁、对象是什么、材料从哪来、决定什么动作、用什么结果判断功能有用
2. **逻辑关系**：明确命题之间的蕴含/等价/相关关系——材料齐全→可计算，可计算→能判断，能判断→能决定
3. **逻辑链条**：把命题和关系串成推理链——从业务问题到规格到实现到验收，每一步都有前一步支撑

一次只改一个案例或实验，不顺手整理无关目录——这本身就是逻辑一致性的实践：不偷换条件，不在一次推理中混入无关变量。
